##### 一 判据①硬前置:两个前提问先答

###### 前提问①:本库变化频度是否达到「需要版本快照」?

**答:频度达到「需要版本化」,但需要的形态是「锚」不是「快照」——要盖,盖的是锚。**

1. Docusaurus 官方适用条件(「文档很少变就别加版本化」)的检验:本库实测 468 commits/日峰值,**远在「很少变」的反侧**,版本化需求成立。这一问的答案=**是,需要**。
2. 但「快照级」三个字要拆开。快照(整份复制)的真实动机是**同时在线服务多个版本给人读**(Docusaurus/RTD 的场景);本库 AI-only(判据⑤),消费方只读当前版,历史靠回溯,**无并发服务旧版场景**。
3. 更决定性的一条:**高频变动恰恰让快照沦为纯成本**——版本间增量账,B 件 §五 已定为四源机器派生(事实页 diff / 规则表「立于版本」过滤 / CHANGELOG 版本段 / 词表行),快照算不出任何四源算不出的增量,只增存储与清理负担。
4. 结论:需求=**封盘时冻结一个可回溯的对齐基准**(「现库标 v0.1 状态、每版跟版本走」),这是锚的语义,不是复制的语义。

###### 前提问②:版本戳打在哪一级?

**答:整库一个戳、与平台版本同号对齐;分层/分项目的细粒度不另立版本序列——它已由既有机制覆盖。**

1. **整库一个戳**。版本总纲 §二 已拍「平台版本为主、⛔ 各模块自造独立版本序列」(代码侧);知识库是平台的镜像,跟平台版本走(代码 `v0.1` ↔ 知识库 `kb-v0.1`),不引入第二套版本坐标。
2. **分层粒度已由三处既有机制覆盖,零新增**:
   - L1 生成物表头 `main@<hash>` 锚——比版本号更细,逐 merge 刷新(version-flow §二.1);
   - L2 规则登记表「立于版本」列(B 件 §三)——**这就是「每模块每条规则立于哪版」的分层账**,monorepo「每组件有自己版本」的功能等价物;
   - L3 frontmatter `status`/`superseded-by`——档级时效链,比版本号更准。
3. monorepo 参照(外证 §五.2):采其**「整体版本」半边**;「每组件独立版本」半边的功能已被上面三条覆盖,再立分层版本戳=同一份账记第二遍,直接撞 B 件 §五 原则。
4. 所以「整体+分层并存」的正确实现=**整体戳(本次新增)+ 分层账(既有,不动)**,而不是两套戳。

##### 二 判据②:三案逐案成本与维护面

**A · 整库快照**——成本:每版整份复制;库体高频变动,快照无限增长、旧版须人工清理(外证 §二 A 格,Spectro Cloud 复盘);本库无 Docusaurus,引入等于新建一套站体系。维护面:三案中最重。与判据④的冲突:**复制=人(机器)写第二遍**,直接违反版本轴原则。**排除。**

**B · 清单+锚**——成本:**无业界现成工具链(外证 §三.1 查无,按必读①读为「须自建」而非「否定」),自建成本计入**:清单格式定义 + 生成脚本 + 校验工序 + 消费端解析规则,四件全要自己写自己养。维护面:一套自建工具的终身维护。致命点:外证 §二 B 格自指「它更像 C 的轻量变体」——而「本版各档各在哪个 commit」这个问题,**git tag→commit→tree 原生就是完整答案**;自建 B = 自费重建 git 功能的子集,零差异化价值。**排除。**

**C · git tag 同仓**——成本:两条 git 命令(`git tag` + 推裸仓),零内容重复,零新工具;业界支柱已实查(RTD 按 tag 自动出文档版本;monorepo tag 前缀成熟)。维护面:≈零(tag 不可变、无清理、无第二份账)。与代码仓版本机制**同构**(总纲 §二 已拍封盘打 `v0.y` tag,V0.1 已兑现 @ `76a1ae9`)。**如实标注的边界一条**:tag 是仓级对象,而 vault 仓大于本知识库(§〇 实测)——戳的语义靠**命名空间(`kb-` 前缀)+ annotated message 声明对齐范围**界定;这不损害功能(git 里本库各档的追溯精确到 commit/tree,与仓内其他内容互不干扰),但语义声明必须写进 message,⛔ 假装 tag 能路径级生效。**采。**

##### 三 判据③:可执行的盖戳方案

**结论:采 C 案(git tag 同仓),知识库作为封盘包第五件,与代码 tag 同轮同号。**

###### 常态化动作清单(V0.2 起,封盘时四步)
1. **前置核**:封盘包第三件(事实表刷新至封盘 main)完成判据达标——逐表核 L1 头行 `main@<hash>` = 代码仓封盘 main(复用 version-flow §二.1 的同一把尺);不新鲜 ⇒ 先刷新再盖,⛔ 带着旧锚盖戳;
2. **打戳**:`git tag -a kb-v0.y -m "知识库 V0.y,对齐代码仓 v0.y @ <代码仓封盘hash>;封盘 <日期>"`(vault 仓 main 上,annotated);
3. **推裸仓**:照 deploy 卡推代码 tag 同法推知识库 tag;
4. **登记**:版本总纲 §四 封盘判据增列「知识库盖戳」为第 5 条、§三 台账增知识库行(知识库 V0.y = `kb-v0.y` @ `<vault commit>`)——两个都是方案窗口管的 wiki 档,改判即更新,不动 11B 的卡。

#### 🔴 攻动一 · 向量①:tag 的「已持久化」判据只证明当下可达,⛔ 证明将来还在

- 方案的验证判据是 `git ls-remote origin refs/tags/laixin-kb-v0.1` **非空 = 已持久化**。
- 🔴 **反对**:`ls-remote` 只证明**此刻该 remote 上有这个 ref**,**⛔ 证明持久性**。而本方案把「可寻址的封盘基线」**整个押在 tag 上**:
  1. **历史重写会让 tag 悬空** —— vault 若做 `filter-branch`/仓损坏修复/**拆仓**,tag 指向的 commit 变悬空对象,`git show laixin-kb-v0.1:<path>` 直接失败;
  2. 🔴 **拆仓不是假想**:vault 是**多项目单仓**(方案 §〇 自己实测的),而本机今日实测 vault 有**数百个未提交改动、混着多个无关项目** ⇒ **未来拆出「来信知识库」独立仓的概率不低**;拆仓后 **tag 名可以带走,但它指向的 commit 在新仓里是新 hash**,tag 须重打,且 filter 后**历史内容未必完整**;
  3. **私有 remote 的持久性无任何保证** —— 方案未说明 `origin` 是什么;若是本地路径或自建服务,**它和 GitHub 那种「几乎不会消失」的假设不是一回事**。
- ⇒ **建议(归合稿判)**:①判据补一条**内容级**验证(如 `git show laixin-kb-v0.1:<某档> | head` 能取到内容),⛔ 只验 ref 存在;②**在方案里显式写下「本方案的可用性依赖 vault 仓历史不被重写」这一前提**,并把**拆仓列为已知失效场景**与迁移动作(重打 tag + 记映射),⛔ 留给未来的人自己撞上。

#### 🔴 攻动二 · 向量③:语义写在 tag 注记里,而最可能的消费路径不经过注记

- 🔴 **反对**:**注记只有 `git show <tag>` / `git tag -n` 才显示**;而方案自己给的**消费约定**是 `git show laixin-kb-v0.y:<路径>` —— **这条命令不显示注记**。⇒ **后任按方案给的路径消费时,恰恰看不到那句语义**。
