## 二 结论:**四条印证 · 零反例 · 一处时点差异(判非反例)**

1. ✅ **tag = 时点快照,是 git 的标准用法**:「Tags in Git are used to **make a snapshot of a repository from a point in time**」(源:[Codeberg · Tags and Releases](https://docs.codeberg.org/git/using-tags/)、[Git Snapshotting 指南](https://dev.to/iredox10/capturing-code-chronicles-a-guide-to-git-snapshotting-557c))⇒ **印证 C 案的核心机制不是自创**。
2. ✅ 🔴 **文档基线的业界做法与 C 案命名同构**:建议「**给已批准文档打版本标签,如 `v1.0-Release-Baseline`**」并将其锁定为官方发布参考(源:[Docsie · Baseline Documentation](https://www.docsie.io/blog/glossary/baseline-documentation/))⇒ **连「tag 名里带 baseline 语义」这一手法都对得上**(C 案=`laixin-kb-v0.1` + 注记写「底座基线」)。
3. ✅ 🔴 **最深的一条印证 —— 恰好命中乙卷的枢纽判断**:**「Baselines do not freeze progress—teams continue iterating; the baseline simply anchors the reference point for measuring that progress.」**(源:同 Docsie)
   ⇒ **业界对 baseline 的定义就是「锚」而非「冻结副本」** —— 乙卷前提问①答的「**需要版本锚,⛔ 需要快照复制**」**在业界定义层面成立**,不只是本项目的权宜。
4. ✅ **IEEE 对 baseline 的正式定义**:经正式评审与同意、**此后作为后续开发的基准**、**只能经正式变更控制修改**(源:[microTOOL · What is a Baseline](https://www.microtool.de/en/knowledge-base/what-is-a-baseline/))⇒ 印证「基线」这个语义选择本身。
5. ✅ **release 会把「代码+文档+发布说明」打成完整快照并产出 audit-ready evidence**(源:[GitLab Releases](https://docs.gitlab.com/user/project/releases/))
   ⇒ 🔴 **顺带印证了我在质疑轮里攻的那一点**:**「审计/回溯」是 release 快照的公认用途之一** —— 即**存在回溯查证型读者**,乙卷「无旧版读者」的前提确实不成立(但 C 案覆盖了它,结论不受影响)。

## 三 一处时点差异(**判非反例**,理由如下)

- **业界建议**:「**在发布前一周**建立正式文档基线,锁定已批准内容作为官方发布参考」(源:同 Docsie);
- **C 案**:**封盘确认后、封盘包其余各件点齐之后**盖戳(方案称之为「收尾针」);v0.1 更是**补盖**。
- ⚖️ **我判非反例,理由**:业界那个「提前一周」是**为人类评审留时间**(「已批准/formally reviewed」是其前提);而**本库 AI-only、且盖戳前置核是「L1 头行锚=当前 main」这种机器判据**,**不需要评审窗口**。⇒ **时点差异源于「有没有人类评审环节」,⛔ 源于机制对错。**
- ⚠️ **但有一句值得带给合稿**:业界把基线定义为「**经正式评审并同意**」的产物,而 C 案的盖戳**没有对应的「批准」环节**(前置核只验事实表新鲜度)。**这不是缺陷,是 AI-only 下的合理简化;但若将来引入人类评审环节,盖戳时点可能要前移。**
