# 调研 · 业界工程度量与多 Agent 沟通开销实践(绑定议题:版本制沟通成本解法议定 的 **拍后补外证**)

## 二 结论(每条带源;⛔ 训练记忆充数)

### 2-1 度量侧(对应「计数纪律」「沟通账」)
1. **DORA 已由四指标演进为五指标模型**(MTTR → **Failed Deployment Recovery Time**);其价值主张是「**先有可测量口径,再谈改进**」,并经多年、跨数千组织验证(源:[dora.dev 官方指南](https://dora.dev/guides/dora-metrics/))。
2. **SPACE 框架五维度中含 `Communication`**,被定位为 **DORA 的补充**——即业界公认「交付指标之外还需单列沟通维度」(源:[Swarmia 实践指南](https://www.swarmia.com/blog/dora-metrics/))。
3. **Flow Efficiency 有明确公式**:`Active Time ÷ Total Flow Time × 100`;**业界基准:多数软件团队仅 15–40%**,即 **60–85% 的时间无人在推进该工作项**(卡在评审队列/等审批/等依赖);高效团队 40–60%,世界级 60–70%(源:[Count.co 定义与基准](https://count.co/metric/flow-efficiency)、[Businessmap 流动效率](https://businessmap.io/kanban-resources/kanban-analytics/flow-efficiency))。
4. **等待被拆成有归因的两类**:`Wait Time`(受制于他人/流程,如卡在评审)与 `Blocked Time`(被具体障碍卡住)(源:[Businessmap 知识库](https://knowledgebase.businessmap.io/hc/en-us/articles/360015452060-The-Flow-Efficiency-Chart))。

### 2-2 多 Agent 侧(对应本项目形态,**比度量侧更直接**)
5. 🔴 **多 agent 系统生产失败率 41%–87%,多数归因于协调缺陷**(规格歧义 / agent 间错位 / 验证缺口),**而非基座模型能力**(源:[Coordination as an Architectural Layer for LLM-Based MAS](https://arxiv.org/pdf/2605.03310))。
6. **协调开销超过总 token 预算的 30%**(典型 hub-and-spoke 设计);**未做 per-agent 成本归因的组织,报告成本比预期高 35–50%**(源:[Zylos 研究 · Agent Observability and Cost Attribution](https://zylos.ai/research/2026-06-14-agent-observability-cost-attribution/))。
7. **通信通道数随 agent 数二次增长**:5-agent mesh = 10 通道,10-agent mesh = 45 通道;且以自然语言消息做 token 级交互虽**利于审计**,却使**通信成为主导成本项**(源:[LLM-Based Multi-Agent Orchestration 综述](https://doi.org/10.3390/fi18060326)、[Communication to Completion](https://arxiv.org/pdf/2510.19995))。
8. **多 agent 研究型系统 token 消耗约为等价单 agent 的 15 倍**,主要来自系统提示重复、工具 schema 开销与 agent 间协调消息(源:[Zylos 研究](https://zylos.ai/research/2026-06-14-agent-observability-cost-attribution/))。

### 三之二 · 唯一一条「建议修正」(⛔ 我直改已拍条文,汇主持走机制变更流程)

**对象=第 9 点里的「A3 门铃日志计数器**挂触发**」。**
**建议**:考虑将其由「挂触发」提前为**近期件**。
**依据(⛔ 我的偏好)**:结论 6 —— **未做 per-agent 成本归因的组织,成本比预期高 35–50%**;结论 8 —— **多 agent 形态本身就有约 15 倍 token 放大**。⇒ 业界证据指向:**计数缺失的代价是「系统性成本超支」,而不是「偶发一次误判」**;而现挂的触发条件是「门铃量需机器计数时 / 人工估数与实际偏差实撞 ≥1 次」,**属偶发型触发**。
⚖️ **反向证据我也如实给**(⛔ 只给支持我的那半):业界那些数字来自**每次 agent 间通信都是一次 LLM 调用**的架构;而**本项目的门铃只传路径、正文走落盘**(总纲 §六「消息只当门铃」),**恰好避开了「通信即 LLM 调用」这个主要成本源** ⇒ **本项目的协调开销可能显著低于业界基准,A3 的紧迫性也就相应低**。**两侧都摆出来,取舍归创始人。**

## 四 十点之外的两条发现(**未被十点覆盖,建议主持判要不要立项**)

1. 🔴 **「协调缺陷而非模型能力是主因」为 11C 的立局前提提供了外部证据**(结论 5)——即**问题出在机制不在模型**。⇒ 这条**支持继续在机制侧投入**,可作总纲/白话层的外部佐证。
2. 🔴 **通信通道数随席位数二次增长**(5 席=10、10 席=45,结论 7)⇒ **对「要不要增加席位」有直接含义**,而十点未涉及。**现行二~三席在此曲线的低位**;若未来扩席,**通道数增长快于席位数**。
