## 二 结论:三种载体各自的业界做法与代价(每条带源)

### 选项 A · 整库快照(Docusaurus `versioned_docs` 模式)
- **做法**:每次发版把当前文档**整份复制**到 `versioned_docs/version-<版本>/`,**历史版本全部留在仓库里**(源:[Docusaurus 官方 Versioning](https://docusaurus.io/docs/versioning)、[facebook/docusaurus 版本化指南](https://github.com/facebook/docusaurus/blob/main/website/docs/guides/docs/versioning.mdx))。
- **代价**:**内容重复**;**旧版本要自己删**,否则无限增长(源:[Spectro Cloud 实践复盘](https://www.spectrocloud.com/blog/when-docs-and-a-dinosaur-git-along-enabling-versioning-in-docusaurus))。
- 🔴 **官方给的适用条件(直接关系到本议题的前提)**:「**versioning 适合高流量、且版本间文档变化快的站;若文档很少变,别加版本化**」(源同官方 Versioning 页)。

### 选项 C · git tag 同仓(ReadTheDocs 模式)
- **做法**:**按代码库上的 git tag 自动生成文档版本**,**不复制内容**(源:[Spectro Cloud 对比](https://www.spectrocloud.com/blog/when-docs-and-a-dinosaur-git-along-enabling-versioning-in-docusaurus))。
- **对照 A 的核心差异**(原文对比):**Docusaurus 需人工快照并把版本存进仓库;ReadTheDocs 按 git tag 自动化、由 release 管理驱动**。
- **monorepo 侧的成熟形态**:**tag 前缀**(如 `myservice/1.3.0`),每个组件**有自己的版本与发布流程**,**同时整个 monorepo 还有一个「整体版本」**;工具链现成(源:[monotag](https://github.com/flaviostutz/monotag)、[Aspect · Monorepo Release Versioning Guide](https://blog.aspect.build/versioning-releases-from-a-monorepo)、[GitVersion monorepo 实践](https://droptable.io/insights/gitversion-monorepo-conventional-commits/))。

### 选项 B · 清单+锚 —— ⚠️ **业界未找到直接对应形态(见 §三 查无 1)**
- **最接近的是「分支式版本化」**:每版一分支,**与源码工作流一致、零内容重复**;**但已知阻碍**=多数 docs-as-code 工具**不支持从多个 git 分支构建同一个站**,因而**每版要各建一个站**(源:[Doctave · Documentation versioning best practices](https://www.doctave.com/blog/documentation-versioning-best-practices))。
- ⇒ **「清单+锚」若成立,它更像是 C 的轻量变体**(不复制内容、只记录「本版对应哪些档的哪个 commit/tag」),**而非业界既有的命名形态**。

## 四 供提案席的对照表(⛔ 选型建议——选型归提案席与创始人)

| | A 整库快照 | B 清单+锚 | C git tag 同仓 |
|---|---|---|---|
| 内容重复 | **有**(整份复制) | 无 | 无 |
| 工具链现成 | 有(Docusaurus) | 🔴 **未见现成**(§三.1) | 有(RTD / monotag / GitVersion) |
| 旧版清理 | **须人工**,否则无限增长 | 取决于自建 | 随 tag 天然存在 |
| 与源码工作流 | 分离 | 取决于自建 | **一致**(tag 即锚) |
| monorepo 适配 | 未见专门支持 | — | **成熟**(tag 前缀 + 整体版本并存) |

## 五 两条我认为主持/提案席应当先看的(⛔ 结论,是**前提性问题**)

1. 🔴 **Docusaurus 官方那句适用条件,是对本议题前提的直接检验**:「文档很少变就别加版本化」。⇒ **提案席应先答:本知识库属于「变化快」那一侧吗?** ⚖️ **我给一个可核的事实、⛔ 替它答**:本库**单日(2026-08-20~21)commit 量为数十次量级**,属高频变动 —— **但「高频变动」是否等于「版本间差异大到需要快照」,是两回事**,后者需提案席自行判。
2. 🔴 **monorepo 那条「每组件有自己的版本 + 整体还有一个版本」与本项目形态高度相似**(知识库分五层 + 多项目入口)⇒ **「版本戳打在哪一级」本身就是待议点**:整库一个 v0.1?还是各层/各项目各自版本 + 整体版本?**本包只指出这个问题存在,⛔ 代答。**
