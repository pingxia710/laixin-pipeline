### a. RFC / PEP / ADR 仓的组织形态

1. **PEP 的编号是编辑席分配的永久身份，过程从 Draft 起步。** PEP 1 要求新文件使用 `pep-NNNN.rst`，`NNNN` 取已发布或 PR 中未占用的下一个号码；PEP 0 另明确号码一经分配不再改变。ADR 的 MADR 约定则是 `NNNN-title-with-dashes.md` 的连续编号；Kubernetes KEP 允许先用 `draft-YYYYMMDD-my-title.md`，重大工作后再分配 KEP 号。来源：[PEP 1](https://peps.python.org/pep-0001/)；[PEP 0](https://peps.python.org/)；[MADR](https://adr.github.io/madr/)；[KEP-0000](https://github.com/kubernetes/enhancements/blob/master/keps/sig-architecture/0000-kep-process/README.md)。

2. **PEP 的 `status` 是显式枚举，并且状态流转带有语义约束。** 已查到的取值为 `Draft`、`Active`、`Accepted`、`Provisional`、`Deferred`、`Rejected`、`Withdrawn`、`Final`、`Superseded`。典型流转是 Draft 进入评审，Accepted 在参考实现进入主代码库后转 Final，Deferred 可回到 Draft；Provisional 在实现反馈后仍可能 Rejected 或 Withdrawn；已 Rejected/Withdrawn/Superseded 的记录仍保留。来源：[PEP 1 的工作流与维护规则](https://peps.python.org/pep-0001/)；[PEPs API 的 status 枚举](https://peps.python.org/api/)。

3. **RFC 的编号更接近出版序列号，不是提案仓内的业务状态号。** RFC Editor 在文档接近出版流程末段分配 RFC 号并正式出版；编号大致递增，但官方 FAQ 说明会因“号码先发出、文档后来未出版”产生缺号。RFC 的状态按流/类别表达：标准轨有 `Proposed Standard`、`Draft Standard`、`Internet Standard`，非标准轨还包括 `Experimental`、`Informational`、`Historic`、`Best Current Practice`；出版后状态仍可改变，变化由 RFC 信息页和 status-changes 记录。来源：[RFC Editor 如何产生 RFC](https://www.rfc-editor.org/authors/rfc-how-to/)；[RFC FAQ](https://www.rfc-editor.org/series/rfc-faq/)；[RFC Index](https://www.rfc-editor.org/rfc-index/)；[RFC Status Changes](https://www.rfc-editor.org/status-changes/)。

4. **ADR 的状态集合不是跨项目统一标准，但“提案—接受/拒绝—被新记录替代”是重复出现的生命周期。** AWS 的 ADR 过程明确使用 Proposed、Accepted、Rejected，并说明 Accepted/Rejected 后记录视为不可变；若决定改变，创建并评审新 ADR，旧 ADR 改为 Superseded。MADR 模板对状态只给出可选形态示例，包括 `proposed`、`rejected`、`accepted`、`deprecated`、`superseded by ADR-0123`。来源：[AWS ADR process](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)；[MADR 模板与大项目组织](https://adr.github.io/madr/)。

5. **KEP 给出了比通用 ADR 更硬的状态字段与流转范本。** 必填 `status` 只能是 `provisional`、`implementable`、`implemented`、`deferred`、`rejected`、`withdrawn`、`replaced`；`superseded-by` 与 `replaced` 配套。其定义是：provisional=提出并持续定义，implementable=批准实施，implemented=已实现且不再主动改变，deferred=暂不推进，rejected/withdrawn=不再推进但保留历史，replaced=被新 KEP 取代。来源：[KEP-0000 的 metadata 与 workflow](https://github.com/kubernetes/enhancements/blob/master/keps/sig-architecture/0000-kep-process/README.md)。

6. **“不可变过程档”在三类体系中不是同一种强度，但共同点是“不用改旧正文来表达新决定”。** RFC 规定已发布内容不变，变更另发 RFC，并用 `Updates`/`Obsoletes` 关系连接；PEP 在决议后一般不再实质修改，且把正式行为文档维护在 Language Reference、Library Reference 或 PyPA Specifications 等别处；AWS ADR 要求接受或拒绝后不可变，变化通过新 ADR 和旧记录的 Superseded 状态表达。由此可观察到的组合是“旧过程正文保留 + 状态/关系指针可更新 + 当前正典另有消费面”，但这不是本包对来信的适配判断。来源：[RFC Editor What Is an RFC](https://www.rfc-editor.org/series/rfc/)；[PEP 1 的 PEP Maintenance](https://peps.python.org/pep-0001/)；[AWS ADR process](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)。

7. **索引/正典面可以从过程档元数据抽取，也可以由外部出版系统维护。** PEP 0 是全部 PEP 的数值、主题、类别和状态索引，Python `peps` 仓库 README 明确说明 PEP 0 会根据其他 PEP 的 metadata headers 自动生成，PEPs API 另提供只读 JSON 元数据；KEP 将 YAML metadata 明确用于 filtering/display，并以跨索引和可搜索网站作为目标；RFC Editor 提供独立的 RFC Index、信息页和 status-changes 页面。来源：[PEP 0](https://peps.python.org/)；[python/peps README](https://github.com/python/peps)；[PEPs API](https://peps.python.org/api/)；[KEP README](https://github.com/kubernetes/enhancements/blob/master/keps/README.md)；[RFC Index](https://www.rfc-editor.org/rfc-index/)。

8. **索引抽取本身会产生路径一致性问题，不能只凭编号拼 URL。** Kubernetes Enhancements 的公开 issue 记录了 `keps.json` 因 KEP 存在 SIG 下的二级目录而生成 404 的问题；issue 指出数据里已有正确 `Filename`，但下游需要目录字段才能构造正确 URL。这是“正典/索引从过程档抽取”模式的实踩例：身份号、目录路径、状态关系都必须进入索引数据，不能只保存一个名称。来源：[KEP `keps.json` 路径错误 issue #6214](https://github.com/kubernetes/enhancements/issues/6214)。

### b. docs-as-code 的版本化目录惯例

1. **`versioned_docs` 是“当前目录 + 每版快照目录 + 版本导航元数据”的工具化形态。** Docusaurus 执行 `docs:version` 时，把完整 `docs/` 复制到 `versioned_docs/version-<version>/`，同时生成对应 `versioned_sidebars/...json` 并更新 `versions.json`；旧版目录可以单独修改和发布。官方同时警告版本化会增加构建时间和代码库复杂度，适合文档版本间变化快、访问量高的站点，并建议控制活跃版本数量。来源：[Docusaurus Versioning](https://docusaurus.io/docs/versioning)。

2. **`/archive` 是“把完整文档树放进显式历史目录”的目录命名变体，通常还要复制 TOC/索引映射。** Docsy Jekyll 的版本化文档说明将 `_docs` 复制到 `_docs/Archive/<version>`，同时维护版本 TOC、`toc-mapping.yml` 和版本菜单；该文档直接记录了一个旧版本缺少当前新增页面、切换后出现 404 的示例。它还说明版本目录本身是快照，预期不再继续维护。来源：[Docsy Jekyll Versioning your Docs](https://vsoch.github.io/docsy-jekyll/docs/versioning)。

3. **按 release 建目录/文件的本质是“每个版本有自己的内容根和导航边界”，代价是复制与跨版同步。** Antora 将文件夹版本化定义为：每个版本存放在同一 Git ref 的独立目录，由 `antora.yml` 的 `version` 标识；它对作者容易理解，也适用于一个仓库里同时承载许多组件的版本文档，但会失去 Git 对同一文件的跨版本比较、合并和管理优势，每个版本从完整副本开始。来源：[Antora Content Source Versioning Methods](https://docs.antora.org/antora/latest/content-source-versioning-methods/)；[Antora Component Version](https://docs.antora.org/antora/latest/component-version/)。

4. **Git tag/branch 形态提供了另一条 docs-as-code 路径，关键代价从“复制文件”转为“ref、URL 与回补策略”。** Read the Docs 将 Git tag 作为文档快照、长期 branch 作为维护中的 release 分支；版本 slug 来自 tag/branch 名称。官方警告，重命名 active version 会删除旧构建、使旧 URL 404，并要求另配 redirect。来源：[Read the Docs Versions](https://docs.readthedocs.com/platform/stable/versions.html)。

5. **实际维护踩坑集中在“双写、历史构建成本和自动化缺口”。** OpenRemote 的 Docusaurus 维护文档要求：对当前版本也适用的修正要同时改 `docs/<path>` 与 `versioned_docs/version-<latest>/<path>`；patch release 不单独切文档版本。其仓库还记录：从网站移除旧版时，历史 Markdown 仍留在仓库，团队正在研究把旧版本改为独立 artifact 以免每次主站构建全部历史版本；在自动化完成前，版本创建、current 更新和归档仍需人工执行。来源：[OpenRemote documentation README](https://github.com/openremote/documentation)。

### c. 大型项目隔离“过程档”与“正典文档”的做法

1. **PEP 直接把“提案历史”和“正式行为说明”分开。** PEP 1 说明 PEP 文本在版本库中的历史记录用于保存提案演变；决议后，正式行为应维护在 Language Reference、Library Reference 或 PyPA Specifications 等正式文档中。讨论也不塞回正文，而是用 `Discussions-To` 指向公开讨论线程，并用 `Post-History` 记录讨论变更。来源：[PEP 1](https://peps.python.org/pep-0001/)；[PEP 0](https://peps.python.org/)。

2. **Kubernetes 将不同性质的材料做物理分层：KEP 在 Enhancements 仓，会议/议程在 Community，用户正典文档在 Website。** `kubernetes/enhancements/keps` 负责提出、沟通和协调增强项；`kubernetes/community/sig-architecture/README.md` 将会议 notes/agenda、recordings 与 SIG 运营信息作为另一套入口；`kubernetes/website` 的 `content/en/docs` 是面向用户的网站文档。KEP README 另把“跨索引、可搜索网站”列为发现层目标。来源：[Kubernetes KEP README](https://github.com/kubernetes/enhancements/blob/master/keps/README.md)；[SIG Architecture README](https://github.com/kubernetes/community/blob/main/sig-architecture/README.md)；[Kubernetes website repository](https://github.com/kubernetes/website)；[Kubernetes website content example](https://github.com/kubernetes/website/blob/main/content/en/docs/reference/using-api/api-concepts.md)。

3. **MADR 的最小隔离是 `docs/decisions/`：决策档靠近文档但与其他文档分开；大项目可以再按架构/功能分子目录。** MADR 明确说大型项目可能累积数百条决策而难以查找，给出的分类范本是 `decisions/backend/0001-...md`、`decisions/ui/0001-...md`；代价是编号只在分类内唯一。MADR 不强制所有仓库采用同一目录组织。来源：[MADR Applying MADR / large projects](https://adr.github.io/madr/)。

4. **这组实践中，过程档不等于当前正典，索引/状态是两者之间的寻址层。** PEP 使用 PEP 0/API，KEP 使用 YAML metadata 与跨索引目标，RFC 使用 RFC Editor 的信息页/关系字段，ADR 用状态与 supersession 关系；这些来源都把“记录为什么这样决定”和“现在正式怎么做”作为可分离的消费面。此句为跨来源归纳，不是来信的结构建议。来源：[PEP 1](https://peps.python.org/pep-0001/)；[KEP-0000](https://github.com/kubernetes/enhancements/blob/master/keps/sig-architecture/0000-kep-process/README.md)；[RFC Editor](https://www.rfc-editor.org/series/rfc/)；[AWS ADR process](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)。

### d. changelog / release-notes 的目录形态

1. **单文件累积形态以一个 `Unreleased` 入口承接日常变更，再在发布时切成版本段。** Keep a Changelog 的示例是单个 `CHANGELOG` 文件，顶部为 `Unreleased`，版本段带日期；其维护说明认为单文件即使很长通常也可用，若过大可把足够老的历史移到独立文件，但主文件与归档必须双向链接，且不要删除旧条目。来源：[Keep a Changelog](https://keepachangelog.com/en/2.0.0/)。

2. **按版本分文件形态把 release 作为寻址单位。** Kubernetes 的 `CHANGELOG/` 目录实际包含 `CHANGELOG-1.10.md` 至 `CHANGELOG-1.37.md` 等多个版本文件，官方 release notes 页面要求读与 Kubernetes 版本匹配的 Changelog，并同时提供在线筛选。来源：[Kubernetes CHANGELOG 目录](https://github.com/kubernetes/kubernetes/tree/master/CHANGELOG)；[Kubernetes Release Notes](https://kubernetes.io/releases/notes/)。

3. **片段合成形态把“写入”与“发布产物”拆开。** Changesets 将变更意图存为专用 Markdown 文件，累积后由 `version` 计算 package 版本、更新 changelog，再由 `publish` 生成按 package 的 Git tags；其技术说明特别处理 monorepo 内部依赖的连带 bump。来源：[Changesets Versioning and Publishing](https://changesets.dev/guide/versioning-and-publishing)；[Changesets Technical Decisions](https://changesets.dev/guide/technical-decisions)。

4. **Towncrier 是“片段 + 分类 + 合成 NEWS/CHANGES”的另一种实现，片段名携带 issue/唯一标识和类型。** 官方教程示例使用 `newsfragments/1234.bugfix`、`3456.doc.rst` 等文件，构建时按类型渲染到 `NEWS.rst`/`CHANGES.md`；正式构建会删除已经消费的片段。Towncrier 的定位明确是把复杂 developer log 复制成足够面向用户的 news fragment，以减少多人共同编辑一个文件时的合并冲突。来源：[Towncrier 稳定版文档](https://towncrier.readthedocs.io/en/stable/)；[Towncrier Tutorial](https://towncrier.readthedocs.io/en/stable/tutorial.html)。

5. **从来源可归纳出三种形态的消费差异：单文件偏“连续阅读”，按版本文件偏“按 release 直达”，片段合成偏“并行写入后统一发布”。** 这是对上述项目文档所示读写路径的归纳，不是对哪一种形态的优劣裁定。来源：[Keep a Changelog](https://keepachangelog.com/en/2.0.0/)；[Kubernetes CHANGELOG](https://github.com/kubernetes/kubernetes/tree/master/CHANGELOG)；[Changesets](https://changesets.dev/guide/versioning-and-publishing)；[Towncrier](https://towncrier.readthedocs.io/en/stable/)。

### e. monorepo 文档分层与寻址

1. **Nx 的大型 monorepo 目录范本是 flat `packages/` 或 grouped `apps/` + `libs/`，且明确把目录视为导航与 ownership 边界。** Nx 说明 flat 适合项目数量较少或以发布 package 为主的工作区；项目达到几十个后，grouped layout 更利于导航，分组目录还可承载 CODEOWNERS 边界。Nx 同时强调这些是可调整的 conventions，不是硬性要求。来源：[Nx Monorepo Folder Structure](https://nx.dev/docs/kb/folder-structure)。

2. **Jetpack monorepo 将“全仓文档”和“项目代码”分层寻址。** Jetpack 文档说明仓库包含数十个插件、package 和工具：应用代码位于 `/projects/`，全仓通用工具位于 `/tools/`，适用于整个 monorepo 的文档位于 `/docs/`；项目类别继续由 `plugins/`、`packages/`、`js-packages/` 等路径表达。来源：[Jetpack Monorepo Overview](https://developer.jetpack.com/docs/jetpack-development/monorepo-overview/)；[Starting a New Project](https://developer.jetpack.com/docs/jetpack-development/starting-a-new-project/)。

3. **Read the Docs 用“子目录内独立配置”处理单仓多文档项目。** 如果一个 Git 仓包含多个需要不同构建配置的文档项目，可在多个子目录放置 `.readthedocs.yaml`；官方还建议用 conditional build cancellation，避免无关子目录变更触发所有文档重建。通过 subprojects，多个项目可共用站点、搜索索引和域名空间，但保留各自 release cycle，URL 以 `/projects/<alias>/...` 隔离。来源：[Read the Docs monorepo setup](https://docs.readthedocs.com/platform/stable/guides/setup/monorepo.html)；[Read the Docs subprojects](https://docs.readthedocs.com/platform/latest/subprojects.html)。

4. **Docusaurus 用多 docs plugin instance 表达多套文档及不同生命周期。** 官方示例把 Product 与 Community 放在不同 `path`/`routeBasePath`，每个 instance 有独立的 `versions.json`、`versioned_docs` 和 `versioned_sidebars`；Android/iOS SDK 也可各有一套版本下拉。官方同时警告，若每个 instance 很大，最好拆成两个站点，否则修改一套会重建另一套未变化的文档。来源：[Docusaurus Docs Multi-instance](https://docusaurus.io/docs/docs-multi-instance)。

5. **Antora 用 component/version descriptor 把多来源、多组件的内容拼成可寻址的 component version。** `antora.yml` 声明组件名和版本，Antora 可从多个 content source 聚合属于同一 component version 的文件；这说明 monorepo/多项目寻址除了目录，还可以由“组件身份 + 版本身份 + source ref”三元关系承担。来源：[Antora What’s a Component Version](https://docs.antora.org/antora/latest/component-version/)；[Antora Content Source Versioning Methods](https://docs.antora.org/antora/latest/content-source-versioning-methods/)。
