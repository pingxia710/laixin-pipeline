# 来信 · 独立验收卡

> 唯一原则:**不接受自我声明,只接受可复现的证据**。"跑过了""验证通过"不算证据,命令输出和实测轨迹才算。
> 只用于 `/Users/pingxia/来信平台`。交付报告是线索,不是证明。
> 全部红线以 `~/Obsidian/项目入口/来信平台/知识库/索引/wiki-红线清单.md` 为准,本卡只给程序。
> **证据锚定(2026-08-13 事故后立)**:结论里每个数字、每处代码引用,必须能在紧邻的真实工具返回中逐字找到;记不起对应返回的,重新执行工具,**不得凭印象书写**。编造证据比漏检更危险。
> **证据落盘(同日加固,把上一条从靠自觉变成可复查)**:凡结论要引用的输出,一律 `2>&1 | tee <证据目录>/<名字>.log` 落盘再引用——全量两次 `pytest-1.log`/`pytest-2.log`、迁移回环 `migration.log`、自写复现 `repro.log`、范围与红线 `scope.log`。证据目录由 `laixin-lane verify` 建好并写在派单里(`~/.laixin-evidence/<片名>/`)。**派工窗口会用 `laixin-lane evidence <片名>` 复查,回执里的数字 grep 不到就退回重验。**

## 先建立独立的审查面

动手测之前,先读:权威 prompt、它引用的设计、执行总表当前状态、候选分支本身。

- **从独立 worktree 或 ref 级操作审查**,绝不在开发方正在用的工作树里 checkout/merge;
- **要求 `main` 是候选分支的祖先**(`git merge-base --is-ancestor main <branch>`)。不是 ⇒ 退回 rebase,并**重跑受影响的检查**——旧基点上的自测与走查验的是旧页面,结论无效;
- 确认候选只改了它声明的范围:逐项看迁移、共享配置、相邻 UI/API 面有没有意外重叠。
- 🔴 **走查的控制端一律是 `browser-harness`,⛔ 去找 `mcp__node_repl__js` / 内置浏览器工具那一类**(2026-08-19 codex 验收窗两次实撞,第二次逐字报 `BROWSER_NODE_REPL_JS_AVAILABLE=0` 因而跳过走查;11B b7 记档)。**为什么你找不到那类工具**:验收窗起窗时 **MCP 是被有意全关的**(`lane_mcp_off_flags` 把 `node_repl` 等十项 `enabled=false`)⇒ **你报「本会话没有 X 运行时」说的是事实,但那不是环境坏,是控制端选错了**。✅ **正确路径**:`browser-harness` **已在验收窗的允许工具里**(`VERIFY_ALLOW` 含 `Bash(browser-harness*)`),shell heredoc 调用它是标准用法;它会读你环境里的 `BU_NAME`/`BU_CDP_URL`,⛔ 自挑端口 ⛔ 连共享 Chrome。⚠️ **⛔ 因为找不到内置浏览器工具就跳过走查并把它写成打回点** —— 那是把一个自己没做的验证项记成被验对象的缺陷;**走查做不了要停车问派工方,⛔ 写进回执当缺陷**。
- 🔴 **CDP 走查:`BU_CDP_URL` 在而端口无监听 = 你还没起,⛔ 判「环境坏」⛔ 要求派工方提供**(2026-08-19 同形第三例,前两例在开发方、**本例在验收方**;11B 创始人窗口 b7 记档)。**判别表**:①`echo $BU_CDP_URL` **有值** + `lsof -nP -iTCP:<端口> -sTCP:LISTEN` **无监听** ⇒ **你还没起自己的 headless**,照宪法头第 12 条的照抄块起(`PORT="${BU_CDP_URL##*:}"` → `--headless=new --remote-debugging-port=$PORT` → `curl /json/version` 自证);②`BU_CDP_URL` **真的为空** ⇒ 才是起窗器的问题,报出来;③端口**有监听但 `/json/version` 五秒无响应** ⇒ 僵死态,`lsof -t` 精确取 PID、`kill -9`、重建 profile 后重起。④**(2026-08-19 晚补,真实 codex 验收窗实撞)端口有监听、`/json/version` 也答得出,但连接被主动拒绝**(`Connection refused` / `unreachable after 30s`)⇒ **⛔ 判「变量为空」,也 ⛔ 判「僵死」** —— 这两条修法都不对症。**分清方式=换一个观察位置**:从**另一个窗口**跑同一条 `curl http://127.0.0.1:<端口>/json/version`。第三方连得上而你连不上 ⇒ 是**你这个窗口的网络可见性**(代理/沙箱)问题,与环境变量、与被验对象都无关;两侧都连不上 ⇒ 是 **CDP 起停时序**(端口 LISTEN ≠ CDP 就绪),等或按③重建。⚠️ 现场逐字样本:`browser-harness: fatal: BU_CDP_URL=http://127.0.0.1:9889 unreachable after 30s: Connection refused`,而同一时刻 `lsof` 显示 `TCP 127.0.0.1:9889 (LISTEN)`、`/json/version` 返回了完整的 `webSocketDebuggerUrl` —— **fatal 消息本身带着变量的完整值,所以它绝不是「读不到」**。⚠️ **⛔ 把「我连不上」写成「变量为空」** —— 那是**诊断结论不是观测**,而验收回执是合并依据:**开发方误判只是停车,验收方误判会把一个自己没做的验证项记成被验对象的缺陷**。📌 实例:某验收回执写 `BU_CDP_URL_PRESENT=no` 并据此跳过 CDP 走查、写成打回点要求「派工方提供专属通道」;派工方两次实测该窗环境**逐字有值**(`BU_CDP_URL=http://127.0.0.1:9889`)而该端口**无监听** ⇒ 打回点不成立。
- ⚠️ **已知环境差异:`frontend` 的 `npm run test:supply-collab-copy` 在「不位于 `~/` 下的审查树」里必 ENOENT**(2026-08-19 两名验收方各撞一次,11B 创始人窗口 b7 自核记档)。逐字根因:`frontend/scripts/check-supply-collab-copy.mjs:13` 用 `readFileSync(resolve(process.cwd(), "../../Obsidian/项目入口/来信平台/知识库/索引/wiki-供给侧词汇表.md"))` —— **路径按 `process.cwd()` 上溯两级**。⇒ 在 `~/来信平台/frontend` 或 `~/来信平台-b87/frontend` 下解到 `/Users/pingxia/Obsidian/...` **成立**;而审查树若建在 `/private/tmp/.../scratchpad/acc-cand` 之类**不在 `~/` 下**的位置,上溯两级落在 scratchpad 里 ⇒ **文件不存在**。⚠️ **⛔ 把它读成「worktree 下必失败」** —— B 轨开发方的 `~/来信平台-b*` worktree **不受影响**,误读会让开发方以为自己也会撞。**绕过**:把审查树建在 `~/` 下,或跑该测试时 `cd` 到主树 frontend,或临时 symlink;**⛔ 因它失败就判该片有问题** —— 它是环境差异不是代码缺陷,但**要在报告里如实写明你用了哪种绕过**。**根治**(来信侧 B 轨微片料,已登记):路径改用绝对路径或环境变量(与 `laixin-lane` 的 `LAIXIN_KB` 同哲学),⛔ 依赖 `process.cwd()` 的相对上溯。

## 验收七步

**1. 自己跑,不看报告结论**
全量测试**跑两遍**(第一遍验通过,第二遍验无随机污染);迁移片必跑 upgrade→downgrade→upgrade 回环。判据是"**全部 passed 且 zero failed**",不是测试数相等(`unittest.subTest` 计数不稳)。
> 失败样本:Codex 的测试是分三批跑的,合起来才全绿;验收方整跑两次才发现口子。

**2. 报告没提的验证项,就是最该亲手跑的**
把交付报告的"已验证清单"和"本片改动清单"对比,**差集就是你的重点**。至少亲手测一个报告完全没提到的实质风险。
> 失败样本:M-11 报告验证清单恰好漏列 downgrade 回环,而那里正好有真 bug(裸 drop_column 删带 FK 列)。

**3. 声明抽查**
报告说"写了 X",就去看 X 是否存在;说"改了 Y",就 `git diff` 看 Y。
> 失败样本:S3 收口报告称已写验收记录,实际没写。

**4. 界面必须真实走查**
browser-harness 实测,不看截图不看描述;消费者侧核 375px 无横滚;匿名能力必须**无痕环境**(清 localStorage/sessionStorage/cookies)实测;**深浅主题都要看**——`R48` 是唯一"后端测试与 lint 都抓不到、只有肉眼能抓"的红线(自定义底色区块未声明前景色→暗色主题下内容不可读),凡新增底色块的前端片逐块核。**页面能渲染不等于通过。**
> 失败样本:B2 的 Codex 扩展断开没做走查,验收方补做才发现问题;订单-4 的"无注册墙"只有无痕实测才能证;B5 四处浅底区块暗色下不可读(锁定版正文、实得金额、联系方式)。
> 走查报"超时"先怀疑环境:自测端口可能有挂死进程(见《开发环境与运行说明》)。
>
> **"建了单一映射源"≠"所有直出点都改用了它"**:凡验"内部状态→人话文案"类交付,必须**扫渲染后的页面文本并遍历状态全集**,不能只确认映射表存在。三元表达式形态的兜底(`x === "paid" ? "已确认" : x`)最容易漏,`grep "|| status"` 抓不到。
> 失败样本:b11 建了 consumer-copy.ts 且修好订单状态与事件,却漏了资金区——非 paid 状态直出 `pending_confirm`,验收方复走页面才捞出(2026-08-12)。

**5. 红线逐条核**
按本片相关的 R 编号逐条核(见红线清单);可见性问题对 `索引/wiki-主体视角表.md` 逐格核。**"不可见"必须是接口不返回,不是前端隐藏**——用**权限最低的身份**直接打接口验响应体,不看 UI 有没有藏。

**6. 边界核对**
`git diff main --stat`:B 轨必须零迁移、后端仅新增独立只读文件;A 轨确认没碰不该碰的共享文件。

**7. 收尾纪律(2026-08-13 五窗口拓扑后修订)**
- **最后一步必须是**:rebase 到当时 main,并**在 rebase 后的状态上复跑全量**——"验的就是合的";
- **你不合并**。合并权在派工窗口:回执交出 `verify-*` 分支名 · 其 commit · **所基于的 main commit** · 全量结果,由它校验 main 未变后合入;
- 主树被 A 轨 Codex 占用期间,**禁止在共享工作树 checkout/merge**;起后端服务只能从与 main 一致的树起。
> 失败样本:B1 验收时误将分支合入 Codex 正在用的 order-2 分支。

## 问题分级

## ⚠️ 前端片必跑全部 `test:*` 脚本(2026-08-13 新增,验收方自曝的缺口;同日改为不写死数量)

**只跑 pytest + lint + build,看不见前端单测** —— 它们既不在 lint 里也不在 build 里。

**样本**:`供给侧存量映射表收拢` 的验收方第一轮只跑了 pytest 与 lint/build,**漏了四个前端测试**;第二轮顺着"文件零重叠 ≠ 零耦合"这条线查依赖方时才发现 `frontend/src/lib/status-label.test.mjs:3` **直接 `import ./supply-copy.ts`** —— 正是那片改的文件。补跑后四个全绿,但**第一轮的"通过"当时并没有覆盖它们**。

⇒ **验前端片时,当场 `grep '"test:' frontend/package.json` 列出全部 `test:*` 脚本,逐个跑并贴退出码。判据是「全部都跑了」,⛔ 不是「跑满 N 个」** —— 写死的清单会随上游片过期(实撞:`双形态-1b` 加了第 6 个 `test:advisor-upgrade`,而当时四份 prompt 都写死"五个测试";与 kickoff 第 11 条"下游核上游实际交付"是同一条的另一面)。

⚠️ **更一般的做法**:改了 `frontend/src/lib/` 下任何模块,先 `git grep -n "from .*<被改文件名>" -- frontend/src` **查出全部依赖方**,再决定要跑哪些测试。**"文件零重叠"只保证不冲突,不保证不耦合。**

📌 **配套的一条查证手法(同一验收方给的,值得推广)**:要证明"某次 rebase 前后某个子树逐字节未变",**别用推断,用 git 对象 hash**:

```
git rev-parse <commitA>:frontend    # 与
git rev-parse <commitB>:frontend    # 相等 ⇒ 该子树逐字节相同
```

⇒ 相等即可**原样继承**该子树相关的全部判据(逐字校验 / 走查 / lint / build),**重跑零信息增量**。⚠️ 注意 zsh 会把 `$VAR:frontend` 当历史修饰符,要写成 `${VAR}:frontend` 或加引号;并注意 `[ "" = "" ]` 会把两个空值判成"相等"——**取 hash 后先断言非空**,否则是假阳性。


## ⚠️ 浏览器走查脚本的色彩假信号(2026-08-13 新增,一晚两发同族)

1. ⛔ **`bg-gradient-*` / `background-image` 元素上,`backgroundColor` 取到的是祖先的颜色**——渐变只设 `background-image`,`background-color` 保持 `transparent`,脚本回溯祖先就拿到父级白底。实撞:琥珀渐变底白字的 L4 徽章被报成"白底白字 1.00",险些立片去修一个不存在的缺陷。**凡待测元素自身带 background-image,对比度结论一律无效**——跳过并如实标注,或改用像素级采样;
2. **`lab()` / `oklch()` 等新色彩函数,老的 rgb 正则解析不了**(同晚第一发,R48 验收方自修过 rgb 层,渐变层没覆盖到——修好一层不等于修好一族);
3. ⭐ **通则:脚本报出的"极端值"(对比度 1.00 这种)优先怀疑解析器,再信结论**——真正的极端缺陷(主视觉白字白底)通常早被人眼发现;**"脚本发现了人眼从没发现过的显眼问题"这个组合本身就是先自查的信号**。

## ⚠️ 观察项不许挂在裁定分支下(2026-08-14 凌晨,1b 验收方自我认领)

## ⚠️ 无取值即未验(2026-08-14 晨新增,同日两片各撞一面)

> **验收时逐项对照 prompt 验证节的编号。凡该编号对应的取值/命令输出在报告里找不到,一律按「未验」处理并亲手跑** —— ⛔ 不因为报告写了「通过/正确/符合」就跳过;**报告的结论语气不构成证据。**

**为什么判定单位是 prompt 的验证项编号而不是报告的段落**:报告结构是自由的(取值可以写「见上」、可以淹在 1.7k 行日志里),「同条目无取值」不可判定;prompt 的编号是双方共有的清单,验收方本来就要逐项过 —— **举证责任在报告:它要证明自己验过,不是验收方证明它没验。**

**两个样本(同日,对验收方的伤害相同——都得重跑一遍才知真假)**:
- `片三-B`:工作做到了,**报告淹没证据** —— 1.7k 行 seed 噪声,验证节取值一个没贴;
- `双形态-2`:**报告语气强过证据** —— 走查脚本未落盘且未访问升级页,五项判据用结论语气而实际未走查。

📌 配套开发侧软规则在派工窗口 prompt 模板(脚本/走查类验证,脚本本身落盘进证据目录并写明路径 —— **取值可以手写,脚本能被重跑**)。
⚠️ **已知未覆盖,如实登记**:「脚本存在」≠「脚本覆盖了这条判据」(双形态-2 的脚本即使落了盘也没访问升级页)—— 修法需每条判据标注证据来源(`[单元测试]`/`[脚本:路径:行]`/`[人工]`/`[未验]`),但核脚本内容的成本可能超过收益,**待第二个样本再议**(准入规则)。

## ⚠️ 资金族片默认判据:失败后可重试(2026-08-14 新增,方案窗口第六任裁;资金3-1 第 2 次打回触发)

## ⚠️ 判据设计四形态速查(2026-08-18 收编,创始人收班优化轮病灶三①;此前活在 dispatch 台账与交接包,跨任会衰减——卡是跨任跨轨载体)
