## 动手前必须过的六问

**1. 基点对不对?**
`git merge-base main <本片分支>` 是否为当时最新 main?另一轨若已合入且碰同文件,**先 rebase 再继续**。
> 失败样本:订单-4 从 B3 合入前的基点开分支,在旧版名片页上改数据源——真正的代价不是合并冲突,是**它的 browser-harness 走查验的是旧页面,结论无效**。

**2. 这个机制是不是已经有了?**
扫 `索引/wiki-机制复用表.md`。锁版本、原子锁定、只追加账、手工通道、拉取式巡检、通知去重、白名单序列化、公开只读路由、状态机总闸+逃生口、分层授权令牌、留白机制、迁移幂等……有就复用,禁止重造。**新增表、端点、字段、UI 控件之前,先查索引有没有同名同义的。**
> 失败样本:v1 片2 差点重造一套履约链路;执行窗口原话"最贵的错误是重造一套履约链路"。

**3. 这个词是不是我以为的意思?**
扫 `索引/wiki-术语表.md`。高危词:标准品副本≠拼团、服务卡≠数字名片、引流域≠营销台、跟单≠值班、首触≠对象归因、L9≠L8之上。
> 失败样本:"聚合单"歧义差点把 v1 片2 做成拼团。**同名不同义比缺文档更危险,因为没人会去查一个自以为懂的词。**

**4. 相关红线是哪几条?**
查 `索引/wiki-红线清单.md`,把 R 编号写进 prompt 的验收要点(不要重述内容)。可见性问题一律查 `索引/wiki-主体视角表.md`。
> 失败样本:红线此前散在二十余份文档,没人能一次看全。

**5. 会不会上一个假门?**
本片要交付的界面,后端是否都存在?没有后端的输入框、按钮、入口一律**留位不渲染**或明确标注"开发中"(R42)。
> 失败样本:B4 协作页区7 差点做成没有后端的输入框;更隐蔽的一种是"有一句没有兑现手段的话"(页面写"有事先找TA",但消费者没有任何触达入口)。
> ⭐ **第三形态:有承诺没入口,且承诺来自后端**(2026-08-14,dispatch 十二任实测):`orders.py:91` 状态文案已对消费者说"你可以确认,也可以重新选择",而 `pending_reassignment` 在整个 `frontend/src` 零命中——**平台承诺了两条去路,界面上一条都没有**。后端文案经 API 送达页面展示,承诺就已"上线",不等前端写一个字。**核法:grep 后端对外文案里的动作承诺词(可以/请/点击/选择),逐一核前端存在对应入口。**

**6. 有原子争抢的地方,输家怎么办?**
凡设计并发争抢(名额/时段/池内锁定),赢家路径之外必须写清**输家的善后**:他的中间态记录如何收尾、资金指令如何作废、他收到什么通知。没有善后=僵尸单。
> 失败样本:片2a 名额争抢的输家副本停在 locked、挂着未付款指令、消费者收不到任何"没抢到"的通知——测试与静态审查都不会自然发现,是验收方真人并发实测捞出来的(2026-08-12)。

## 轨道与边界(双轨制)

- **A 轨**=后端轨:带迁移、碰 models/config/order_state;

⭐ **每条纪律性要求必须配自证判据(命令+贴输出),只写要求本身等于没写**(2026-08-14 干净对照:同一个 Codex 同一天,片2 的 prompt 要求贴 `git log --oneline main..HEAD` 自证 commit 数≥任务数 ⇒ 五任务五 commit;Caddyfile 片只写了「每任务一 commit」六个字 ⇒ 单 commit 涵三件。**同一条要求,加了自证就被遵守,没加就没有**——与验收纪律节「纪律行没有判据等于没有要求」同一条定律的开发侧写法)。

## ⚠️「每任务一 commit」的整改轮口径(2026-08-20 立,方案窗口第十六任裁、dispatch 43 拟稿;实证=R1 第 3 次打回,根因=判据没考虑整改轮的存在)

**每任务一 commit**是**交付时**以任务为单位的形态要求;**整改轮必然产生新 commit**,两者不冲突,口径如下:
- 整改轮追加的 commit **归属它修的那个任务**;
- 若整改跨任务、或验收要求保持一任务一 commit,**交付前 squash 回该任务的 commit** 并在报告说明(commit 数/末行/分支 HEAD 三处同轮更新);
- **⛔ 让整改轮的追加 commit 成为下一轮打回项**——那是拿判据的缺口惩罚照办整改的开发方(实撞:R1 第 2 轮整改指令要求把四条挂进 lint 链=天然追加一个 commit,第 3 轮验收按「每任务一 commit」字面打回)。

## ⚠️ 别用会静默变成假阴性的验证命令(2026-08-13 新增,派工窗口自述)

```bash
# ❌ 反例:看起来像做过验证,实际是假阴性
git show main:app/models/category.py 2>/dev/null | grep -n clarification || echo "❌ Category 上没有"
```

**`category.py` 这个文件根本不存在**,错误被 `2>/dev/null` 吞掉 ⇒ grep 空输出 ⇒ 触发 `||` 分支 ⇒ **"文件不存在"被读成了"字段不存在"**。派工窗口据此在 prompt 里写了一条错误更正,发车前被方案窗口拦下。

**它自己的评价**:"这条比单纯看错行号危险,**因为它看起来像做过验证**。"

三条规矩:
1. **`2>/dev/null` 只用在"确实预期会有噪声"的地方**,不要用在验证命令上——你要区分的正是"没有"和"出错";
2. **验证存在性时,先确认载体存在**:`ls` 到文件、`grep -n '^class'` 定类边界,再查内容。`git grep` 只回一个 `文件:行号` 时,**行号属于哪个类要靠类边界判,不能靠文件名推断**(`Category` 类就定义在 `demand.py` 里);
3. **`|| echo "没有"` 这种兜底句式,把命令失败和结果为空混成了同一个分支**——要么分开判 `$?`,要么别用它下结论。
4. **第一次搜索的零命中不是结论,是"换个范围再搜"的信号。**
   **样本**:写 `打标台界面` prompt 时,派工窗口搜 `git grep 'order_tag_values' main -- app/routers/` 得零命中,据此判定"**枚举值域没有出口 ⇒ 设计要求的『读配置零硬编码』做不到 ⇒ 需要先开一个 A 轨前置片**"。穷举复核(搜整个 `app/`)才发现 —— `serialize_order_tags`(`app/services/order_tagging.py`)**返回体里早就带着 `allowed_values`**,随 `GET /tags` 一起给了前端。**差一点就登记一个完全多余的片。**
   ⇒ **搜索范围写窄了,和"东西真的不存在",输出完全一样。** 判"某能力不存在"之前,**至少把范围放宽一层再搜一次**(`app/routers/` → `app/`),或换一个必然出现的关键词交叉验证。**这条和"匹配宁可放宽不要收窄"是一对**:收窄正则会漏掉真违规,收窄路径会造出假缺口。

## ⚠️ 切"纯后端片"前,先核前端是不是通用渲染(2026-08-13 新增)

**一句话:数据形状的新增就是界面变更。**

**样本**:`打标可见性与队列露出` 被切成"**纯后端**"片,prompt 写死"不改前端"。它给 `/api/me/todo` 新增了一个 `order_tagging_required` section —— **一行前端代码没改**,但顾问待办页立刻出现:

```
order_tagging_required 4          ← 英文 key 直出
查看详情                            ← 兜底文案
"进入" → /                         ← 死链
```

根因:`frontend/src/app/todo/page.tsx` 是 `Object.entries(todo.items).filter(items.length>0)` **通用渲染所有非空 section**,取不到 `sectionMeta` 就兜底 `{title: key, description:"查看详情", href:"/"}`。⇒ **后端多一个 section,界面就多一块;而那块的文案是英文 key**,与当天刚合入的"消灭英文直出"红线片正面冲突。

**开发方不改前端是遵守 prompt 的**;错在切片假设 —— 派工窗口以为"后端/前端"是一条干净的缝,实际那里没有缝。

**通则(写 prompt 前逐条问)**:
1. 我新增的**数据项**(section / 字段 / 枚举值 / 列表项)会不会被前端的**通用渲染层**自动显示?
2. 那个渲染层有没有**兜底分支**(`|| key`、`{title: key}`、`?? "-"`)?**兜底就是英文直出的入口**;
3. 若两者都是"是" ⇒ 这**不是纯后端片**。要么把配套的一行文案/映射纳入本片范围,要么**明确写出"本片上线后界面会出现 X,由下一片收口"并让方案窗口确认可接受**;
4. **反向也成立**:删掉一个后端字段/枚举值,通用渲染层可能从"有值"变成"空/`-`",而那也是界面变更(参见同日 `deliverable_type` 采集断档:后端移除采集入口,商会审核台与消费者页**静默显示空**)。
5. **后端放开/收紧一条数据规则时,"纯后端"这个边界大概率不存在**:前端的**校验、渲染、提交**三处往往各握着同一条规则的副本,后端单方面改,三处同时变错(实撞 2026-08-13 夜:`争议单异常标记与补填` prompt 写"零迁移纯后端",后端豁免 `consumer_present` 后,前端表单仍无条件强制/渲染/提交它 ⇒ 顾问只能猜一个不适用的值;该片被迫**两次**中途扩前端边界)。⇒ 切片前先 grep 该字段/规则在前端的三处副本,**有副本就把配套改动写进同一片射程**,不要指望"后端先行、前端后补"。

## ⚠️ 验证项怎么写(2026-08-13 新增,派工窗口一天内攒的五条,每条都有失败样本)

> 上一节讲"别用会静默变成假阴性的**命令**",本节讲**验证项本身怎么设计**。共同点:**"跑过了"和"验到了"不是一回事。**

### 1. 对称验证:正向证明修好了,反向证明没修过头

**样本**:`公网加固校正` 要把限流校验从 `0 < auth < public` 放宽成 `auth <= public`。只写正向验证(`public=50` 时应用必须起得来)会漏掉一整类失败——**改松过头**。故配一条反向闸门:`auth=60 / public=50`(登录桶比公开桶宽松)**仍必须拒绝启动**。

**通则**:凡是**放宽/删除/兜底**类改动,验证项必须成对——①改动生效了;②**改动没有连带削掉它本该保留的保护**。只有正向那一半时,"修好了"和"拆掉了"在输出上长得一模一样。

### 1-bis. 错误路径判据要断言「**失败之后系统还能用**」,不只断言「失败时返回什么」(2026-08-14 新增,资金3-1 第 2 轮打回)

**样本(资金静默失败,329 个用例全绿没抓住)**:`资金3-1 适配层先行` 把确认收款改造成经适配层走。改造后:一次确认收款因业务校验失败返回 409 —— **正确**;但那次失败**在 `PaymentCallback` 表里残留了一行**,幂等键 `manual:<payment_order_id>` **被永久占用**。⇒ 运营修复数据后**重试**:HTTP **200**(看起来成功了),而**账户仍 `pending_confirm`、charge 仍 `pending`** —— **钱没进账,而且这个托管账户此后再也无法通过接口入账**。基线树同一脚本重试则正常入账。

**为什么 329 个用例全绿**:新增的两条错误路径用例**都止步于「失败时返回 409」**,**没有一条断言「失败之后还能重试成功」**。⇒ **判据的射程停在了错误响应上,而伤害发生在错误响应之后。**

**通则**:
1. 凡新增/改造**会写库的失败路径**,判据必须有第二步:**失败一次之后,把导致失败的原因排除掉,再走一次同一条路 —— 它必须能成功**;
2. 尤其当路径上有**幂等键、锁、去重键、状态机跃迁**时:问一句「**这次失败,有没有在库里留下一个会挡住下次的东西?**」;
3. **与基线树对比**是最省事的判法(同一份脚本在 main 与分支各跑一遍),⛔ 不要只在分支上自证;
4. ⚠️ **配套**:证明「没有残留」的探针最容易写成无效的。同片实撞两种(**验收方明说不是造假,是探针写错**):①探针在调用前**先改了状态字段**,于是命中了另一条事务情形才得零残留;②探针用 `patch.object` 把被测函数整个换成抛异常的 mock,**根本没执行到插入那一步**。⇒ **探针必须走真实调用路径,并在「什么都不改」的条件下观察库里剩下什么。**

### 1-ter. 关系判据的样本值必须能让「通过」与「失败」分开(2026-08-23 新增,包①「钱的去向」验收观察项;方案窗口第二十三任出句、11B 落)

**样本**:包①三数关系判据(应付 / 实付 / 比例)首轮用 `299.00 / 299.00 / 100%` 复核——三数恰好相等,**「关系算对了」与「三处在显示同一个字段」在报告上不可分辨**;后以四数各异样本复核才真正通过。

**通则**:凡判据断言的是**多个值之间的关系**(等式 / 比例 / 差额 / 先后 / 去重 / 映射),样本值必须选成**关系不成立时数字会不同**的形态——退化样本(全等 / 全零 / 全空 / 同源字段)让「验到了」与「恰好同形」同形。写 prompt 时给样本值同时给一句「为什么这组值能分开通过/失败」;**资金族片每条关系判据至少一组各异样本**;与 §10 反事实自检同源(10 问「性质不成立时判据会不会失败」,本条管的是**让它有机会失败的数据**)。

### 2. 抄来的验证项也要核(**模式的构造性歧义**)

**样本**:`状态词补齐` 的复扫判据 `git grep "|| status\||| order.status\|…"` 是从上一片 prompt 抄的。但 `|| order.status` 会**同时匹配两种性质相反的形态**:

```
labels[x] || order.status                                    ← 渲染兜底:把英文原值显示给人看(真违规)
isAdmin && (order.status === "a" || order.status === "b")    ← 布尔条件:一个字都不渲染(无关)
```

Codex 因此被一条**构造性假阳性**的"零命中"判据卡住,并**正确地拒绝为通过检查而改产品行为**。

**通则**:**宽扫不收窄,但判据要带二分判定** —— 让开发方对每条命中标注类别(真违规/无关形态),判据只对真违规类要求归零,无关形态**允许命中但须逐条列出**。收窄正则去凑零命中,只会把真违规一起漏掉。

### 3. 判据里的数字必须无歧义、可逐格 grep

**样本**:派工窗口写"鉴权矩阵 **12 格**(六身份 × GET/两 PUT)"——六身份 × 三端点应是 **18 格**,含混处在"两个 PUT 算一组还是两格"。被方案窗口拦下。

**通则**:验收方**不该替派工窗口解释判据**。凡涉及计数,把整张期望矩阵/清单**逐项写死进 prompt**,并给出通过条件(如"恰好 1 格变化,其余 17 格逐格一致;少贴一格即不通过")。

### 4. 生产配置下的防护 ≠ 测试配置下的防护

**样本**:`速率限制铺开` 的新用例**全把阈值改成 1/2 才触发 429** —— 那证明的是"限流代码能跑",不是"生产默认配置下真的挡得住"。验收方**不改任何配置**连打 55 次,才拿到"第 51 次首次 429、200 次数=50"这个真答案。

**通则**:安全/限流/闸门类片,验证项必须含一条**在生产默认配置下**的实测;顺带**要定量不要是非** —— "过了"和"余量多少"是两个信息(该片实测 auth 桶峰值 28/阈值 50,余量 22 ⇒ 才知道下次加用例会不会撞线)。

### 5. 走查证据必须附"页面真的渲染出来了"的自证量

**样本**:`状态词兜底清理` 的走查用 3117 端口,撞上后端 `cors_origins` 默认只放行 3000/3100 ⇒ token 被清空、**页面全空** ⇒ 扫描"无英文状态词"通过,实为**假阴性**;而报告**未贴页面文本长度**,其走查证据**无法从报告本身自证**。

**通则**:凡 `browser-harness` 走查,报告须附**页面文本长度**(或元素计数)这类自证量。**空页面扫不出违规,和真的没有违规,输出长得一模一样。**

### 5-bis. ⛔ 退出码 0 不是「成功」的证据 —— 成败一律以**产物/取值**为准(2026-08-14 新增,方案窗口 M5 C 族;dispatch 十三任落卡)

**样本**:`消费者确认换人页` 验收方在 `/private/tmp` 建验收树、`node_modules` 用软链,**Turbopack 报 `Symlink ... points out of the filesystem root`——而 shell 退出码仍是 `0`**。⇒ **构建其实失败了,报告若只贴 `BUILD_EXIT=0` 就是一份自信的假绿。**(2026-08-15 二次实撞同触发条件,补自证方式:**build 后贴 `.next/BUILD_ID` 内容与页面产物存在性**——产物级自证一行,比事后排查便宜)

**这与「端口撞了静默退出」是同一族**(`next start` 撞口静默退出、浏览器打开的是别人的 main 版页面),都属**工具用非零退出码之外的方式失败**。

**5-ter 补(2026-08-15,等级徽章片验收方捞出)**:**「渲染逐字不变」不是纯重构的完备判据**——映射从 `.tsx` 移入 `.ts` 时,若 Tailwind 内容扫描不含 `.ts`,**class 名还在而颜色消失,outerHTML 逐字比对抓不到**(样式生效与 DOM 不变是两个维度)。纯重构片的判据须补一条**样式生效证据**(构建产物 CSS 含该 class,或截图/computed style 抽查),该轮验收方双向自证探针后 `HIT=16 MISSING=0` 即此形态。

**分支维度补(2026-08-18,方案窗口第十任裁;5-ter 管样式维度,本补管分支维度)**:**文本正确与分支正确是两个独立维度**——N 句文案逐字全对,不等于 N 句挂对了位置;凡改动含条件渲染,判据须做**分支组合求值**(嵌套条件全组合各验上屏句),⛔ 只做逐字比对——**逐字比对会全绿通过一个句子串位的界面**(做反了=点「通过」弹出打回句,而每一句单独看都是词表正确文案,逐字比对对此零分辨力)。样本:核稿页片 `3bf7a90` 四句 toast 挂嵌套三元,报告证了四句逐码点全对(BYTE_EXACT_MATCH_ALL_4)、零证挂对位置;验收方补跑三元优先级四组合求值才补上这一维。

**通则**:
1. **构建成功以产物存在为准**,⛔ 不以退出码为准 —— 报告须贴产物证据(`.next` 之类的目录/文件列表或大小),`EXIT=0` 只是必要条件;
2. 同理适用于**起服务**(查进程还在不在,不只看 curl 通不通)、**迁移**(查表真的建了/真的消失了,不只看命令返回)、**测试**(看 `passed/failed` 计数,不只看退出码);
3. 写判据时问一句:「**这个工具失败的时候,一定会用非零退出码告诉我吗?**」答不上来,就去找一个**正向的产物证据**。

### 6. 转述进 prompt 的断言也要核

**样本**:派工窗口把"`nav.tsx:57` 那个徽标**永远为 0**"写进 prompt —— 该句来自另一窗口的消息,未自行复核;验收方核出徽标是**多 key 求和**,无效 key 只贡献 0,**实测该徽标为 1**。

**通则**:**prompt 里的每句话在 Codex 眼里都是事实。** 转述来的结论、抄来的判据、上游窗口给的定位,进 prompt 前一律自己跑一遍命令;核不了的,写成"待核"而不是写成事实。

### 7. 引用索引表要**引全**:词和它的维护约定是一套

**样本**:写 `供给侧枚举收口` 的 prompt 时,派工窗口读了 `wiki-供给侧词汇表` **§六 取词**(哪个内部值显示成什么),据此写出"新增 `reviewStatusLabels`,仿照同文件既有映射表**放在 `workbench/page.tsx` 里**"。

但**同一张表的 §维护约定**写着:"代码侧以 `frontend/src/lib/` 的映射常量为**单一出口**,**页面内不得散写**。"

⇒ prompt 的做法与索引层**正面冲突**。开发方按 **"索引表 > prompt"** 的裁决顺序停下来报告,**它是对的**;派工窗口认错并请方案窗口裁了落点。

**根因不是粗心,是取用方式**:索引表被当成**查词的字典**用了 —— 查到词就走,没看这张表**对怎么用这些词还有规矩**。

**通则**:
1. **从索引表取任何东西之前,先读完这张表的"维护约定 / 使用规则"节**;词、规矩、落点通常写在同一份文件的不同节里;
2. prompt 里凡是写"**放在哪个文件 / 怎么组织**"的句子,都要回索引表核一遍有没有既定出口 —— **这类句子最像"实现细节"、最容易凭手感写,而它恰恰常常是被规定死的**;
3. 若索引表的规矩本身**含混**(如只说"`lib/` 的映射常量"而不指名文件),**这是索引层的歧义,报方案窗口钉死具体文件名**,不要在 prompt 里替它做决定 —— 本次即如此处理,歧义已在源头消除。

### 8. 判"这里是违规"之前,先核**它实际显示出来的是什么**

**样本(造成了真实功能回归,不是虚惊)**:`供给侧枚举收口` 的 prompt 里,派工窗口把 `deliverableTypeLabels[x] || x` 列为"回落英文原值的兜底"要求消灭。开发方照做,换成中性兜底。

**但后端 `deliverable_type` 写入的值域是中文**(`config.py` 的 `order_tag_values`:实物/现场服务/文档方案/数字资产/混合,唯一写入路径受 `validate_tag_values` 强校验;前端那张英文映射表**与后端值域交集为空**,四个英文键实测全被 REJECT)。

⇒ 改之前 `|| x` 兜出来的是**「实物」这类可读中文**,**根本不违反 R10**(R10 禁的是英文枚举);
⇒ 改之后显示**「状态更新中」**,**信息丢失** —— 一次"修复"制造了一个回归。

**根因不是粗心,是判定方向反了**:派工窗口是**从代码形态**(`|| x` 这个写法)推断"它会显示英文",而**没有从数据**(这一列实际存的是什么)去验证。**形态相同的两处代码,数据不同,一处是违规、一处是正确写法。**

**通则**:
1. **凡是要求"消灭某处兜底 / 改掉某处显示",先查这一列的写入点,确认它实际存的是什么**——`git grep` 该字段的赋值点与值域配置,而不是只看渲染处的写法;
2. **"回落原值"是不是违规,取决于原值长什么样**;原值本身是中文人话时,回落是**正确的降级**,把它换成中性词反而丢信息;
3. ⚠️ **这条和"词表是应然、写入点是实然,两边都要扫"是同一条**——只是这次犯在派工窗口自己身上:**同一天里,写 prompt 的人刚把这条要求写给开发方,自己却没做。**
4. ⭐ **同一个错的第二种发作:判断"这个界面入口可达"时,要核的是状态链,不是代码形态。**
5. ⭐ **第三种发作(2026-08-18 dispatch 二十二任险犯后补):判「某处违规」前先确认共用层有没有把它接管掉**——按登记数「裸 `<SelectValue />`」得 11 处差点立片,实际包装层(`select.tsx` selectItems 收集 value→label)已自动映射,裸写法不再等于违规;**`git log -S <机制名> -- <共用件>` 是最快的探针**。与同晚 setattr 假零命中同族:登记写下时为真的「违规形态」,会被后来的共用层修法整体接管而失效,**形态还在、违规已死**。
   **样本(同日,方向性打回)**:`打标台界面` 把收单打标表单挂进了「标准化」Dialog —— 派工窗口核的是**代码形态**:有「标准化」按钮 → 打开 Dialog → 提交 `/standardize`,于是认定它就是设计说的"收单确认步"。
   **没核的是状态链**:该按钮的条件是 `demand.status === "advisor_engaged"`,而**建单动作本身会把 demand 置成 `LOCKED`** ⇒ **建单后按钮就消失了**;全仓唯一把它置回去的写入点是"商家退回需澄清",**而那时订单已是终态、表单只读**。
   ⇒ 实测结果是 **「可打开」与「可填写」互斥**:9 张需求卡里按钮只出现 1 次,且打开后 8 个控件全 disabled。
   **通则**:把功能挂到某个既有入口上之前,**追一遍这个入口的显示条件在目标时刻还成立不成立** —— 具体做法是:①找到该条件字段的**全部写入点**(`git grep` 赋值);②问"**我要用它的那个时刻,这个字段是什么值**";③若入口条件与功能所需状态**互斥**,这个落点就是错的。**"这里有个按钮和一个 Dialog"不等于"用户在需要它的时候能看到它"。**
5. 📌 **还有一层时序教训,它需要的是一个动作而不是更强的自觉**:该派工窗口**后来写另一片 prompt 时确实看到了那份中文值域配置**,但**没有回头检查已经发出去的 prompt** —— 规则早已上墙("两边都要扫"),**上墙不等于生效**,因为新知识到达时,已发出的 prompt 已经变成了**带病存量**。
   ⇒ **钩子:每当你核到一个新事实(值域、接口形状、字段语义),当场问一句"它推翻了我写进哪份 prompt 的判断吗?"** 在飞的、已排队的都要扫。**这一步花十几秒,漏掉它的代价是一个功能回归。**

### 8-bis. 「渲染条件」⛔ 等于「可达条件」——判某个界面状态可不可达,要追数据到达渲染层之前的过滤

**样本(2026-08-23,dispatch 第六十一任写 prompt 时自撞,代价=开发方停车一轮)**:我核了 `frontend/src/components/home-supply-flow.tsx` 组件内的**两层渲染条件**(`:76` `chambers.length === 0` 整块 `return null` · `:97` `members.length > 0` 成员卡),据此写出判据「只有商会、没有成员 ⇒ 出商会行、不出成员卡」。
而 `:45-46` 在**数据加载阶段**就 `filter((chamber) => chamber.chamber_type === "service_provider" && chamber.member_count > 0)` ⇒ **零成员商会根本进不了列表**,那个状态**在当前实现下不可达**。开发方拒绝在「改前端」与「伪造 `member_count`」之间自选(两者都超授权),**停车正确**。

⭐ **一句话**:**组件里写着 `if (x 为空) return null`,⛔ 说明「x 为空」这个状态可达** —— 数据在到达渲染层之前可能已被过滤成永不为空,或永不满足某个组合。**渲染条件描述的是「如果发生会怎样」,可达条件才决定「会不会发生」。**

**动作**:凡 prompt 判据要求「某界面处于某状态」,**从数据入口往下追一遍全链过滤**(API 调用 → `filter`/`slice`/排序 → 组件条件),**每一层都记下来**;判据只能落在**全链都可达**的状态上;**拿不准就把判定交给开发方并写死兜底**——「该态可不可达由你实测判定;**不可达即明写不可达并给依据,⛔ 造假数据去凑一个现实中不存在的状态**」。

📌 **与既有条的分工(⛔ 混为一谈)**:第 8 条治「**从代码形态推断数据**」(看渲染写法猜数据长什么样);**本条治「只核了链条的一段」** —— 两段代码都读对了,错在**没读它们之间还有一段**。与 13-bis「改读法前列全读者」**互为反向**:那条向下游列读者,本条向上游追过滤。
⚖️ **它与 `laixin-pipeline` 卡「互相复核不能替代各自追赋值处」的区别**:那条射程是**跨窗口复核**(三方读同一句未经验证的转述);本条是**单人写 prompt 时核现场**,没有第二个人参与。落卡前实测过 kickoff 侧对「渲染条件 / 可达条件 / 数据加载阶段」零命中。

### 9. 扫描判据要覆盖"**无兜底的裸直出**",别只扫兜底形态

**样本**:同一片的 P1。prompt §验证项要求"宽扫 `\|\|` 与 `??` 兜底形态,逐条二分判定"。开发方**照判据执行**、得出"渲染兜底类为零",**执行没有问题**;但 `{chamber.staff_role}` 这种**根本没有兜底的裸插值**,**结构上就不在这个判据的射程内** ⇒ 页面照样直出 `reviewer`,违反 R10,**而且就在本片的目标文件与主题内**。

**通则**:查"英文直出"至少要**两类模式并列**,缺一类就是盲区:
- **(A) 带兜底的**:`labels[x] || x`、`?? x`、三元回落;
- **(B) 无兜底的裸直出**:`{obj.some_role}`、`{obj.type}`、`{obj.status}` 这类**直接把字段插进 JSX**的写法 —— 它没有任何"兜底"痕迹可供 grep,**要按"字段名被直接插值"来扫**。

⚠️ **判据漏了一类,开发方交回的"零命中"就是真诚且无效的**。写判据的人要为盲区负责,不是执行的人。

### 10. 判据必须在"被测性质不成立时失败" —— 反事实自检

**样本**:`公网部署收尾` 要求 `/healthz` **豁免限流**。派工窗口在 prompt 里把判据钉死为:「**打满公开层限流(打到 429)后,紧接着请求 `/healthz` 仍须 200**」,还特意写了"这是唯一证明方式,看代码加没加豁免不算"。

**这个判据是无效的**:三个限流桶是**独立字典**,`/healthz` **从未进过任何桶** ⇒ 打满 `/api/chambers` 的桶,本来就不会影响它。**假如 `/healthz` 根本没被豁免、只是恰好不在那个桶里,这个判据照样全绿。**

验收方补的**真**证明是两条:
1. **连续请求 `/healthz` 180 次(3 倍上限)全 200** ⇒ 证明**它自己**不被限流;
2. **打满这 180 次之后,公开桶仍有完整 60 次配额**(第 61 次才 429)⇒ 证明它**没有消耗**公开桶。

**通则 —— 写完每一条判据,做一次反事实自检**:

> **"假如我要证明的这个性质根本不成立,这条判据会不会照样通过?"**
> 会 ⇒ 判据无效,重写。

**判据无效的三种常见长相**(都出现在本项目):
- **因果链断了**:测的现象与被测性质之间没有必然联系(本例:打满 A 桶证明不了 B 的豁免);
- **被测对象是空的**:空列表 / 空页面上扫描,"扫不出违规"与"真没违规"输出相同(b17 CORS 页面全空、`order_messages` 空表);
- **射程没覆盖**:判据只匹配一部分形态,漏掉的那类照样违规(只扫兜底、漏掉裸插值)。
- **只沿生产侧枚举,没沿消费侧反查**(2026-08-18 补,桥片验收逼出,「射程没覆盖」的一个高频成因;dispatch 与方案窗口各认半):判据表沿「我改的这个函数做了什么」枚举,没问「**还有谁在别处读这个状态/字段来算指标**」——桥片 V5-bis 只断言五项递增式字段取值,反事实一问「假如退款单仍被算作成功履约根本没修掉,判据会不会照样全绿」答案是会。⇒ **写判据先列消费者清单**(谁读它:统计口径/榜单/结算/看板),每个消费点至少一条判据。⭐ 配套强判据形态=**同构对照**:full 与 none 两条路各跑一遍看 delta,⛔ 只在一条路上看绝对值(本次验收方即靠它抓到)。

⚠️ **三种都有同一个症状:绿灯不代表做对了,只代表这条判据没抓到。** 判据要设计成**性质不成立时必然变红**。

**"射程没覆盖"的两个新现场(2026-08-13 晚补 —— 同一个病在两个层面发作)**:

1. **在片的验收里**:`打标台界面` 上一轮正反两向都跑在 **≤2 条样本**下,而缺陷(`items.slice(0, 5)` 致第 6 条起没有任何入口)**只在 >5 条时出现** ⇒ **判据的射程与缺陷的分布不重叠**,全绿通过。⇒ 本轮硬要求**待打标条目 ≥7 条**,**只在小样本下验出的结论一律不接受**。
2. **在流水线自身的测试里**:事件总线的执行级测试是「`ev_watch_target` 在窗口不存在时**实跑不炸**」——**它对"该不该告警"零分辨力**。lane-b 窗口整个消失、空转 17 分钟那会儿,**这条测试是绿的**。

⭐ **怎么把"绿了"分成两类 —— 把改动还原,再跑一遍**:
- **绑定改动的判据 ⇒ 变红**(证明它真在测这件事);
- **回归保护型判据 ⇒ 两种情况都绿**(它的作用是"确保没把正常行为改坏",本就不该有分辨力)。

⇒ 修完事件总线后实际做了这一步(`git stash` 还原 → 跑测试 → `stash pop`):**3 条新判据全红、1 条静默保护仍绿**。**不还原一次,你分不出自己写的是哪一类。**

**10 之二:堵洞类修复的判据必须配对(2026-08-14,㉚ 防火墙静默放行案)**:修"静默放行/静默失效"类缺陷,单跑「现在拦得住」只能证明**现在是对的**,证明不了**以前是错的**——而"以前也不错"意味着你可能修错了地方。⇒ 判据配对:正向证明现在拦得住 + **在改动前的代码上跑同一构造、证明它当时放行**(㉚ prompt 第 9/10 条即此形状;缺后半即无效)。

### 10-ter. 防线类/收敛类片:变异测试验「既有防线还活着」(2026-08-14 夜,排除集补全片验收方首创)

「把改动还原再跑」(第 10 条)验的是**我的新判据有没有分辨力**;**变异测试**验的是**我依赖的既有防线还活着**——在 main 基线注入一个反向错误实现(如「把所有后任都塞进排除集」),跑既有反事实测试,**必须全红**(还原后全绿)。样本:排除集补全片验收方注入变异后三条反事实 FAILED(failures=3),证明那三条是真防线而非装饰。**写收敛类/防线类片 prompt 时把变异自检列入验证项**:指明注入什么变异、哪些测试必须变红。

### 10-ter. 判据设计四形态速查(2026-08-18 收编,创始人收班优化轮;写判据时逐个过「用得上吗」)

**同构对照**(两路同脚本看 delta ⛔ 单路绝对值,第 10 条第四长相配套)· **探针翻转**(核查类探针**使用前先自证**:已知阳性命中/全集数目对照,⛔ 现写直接用——不限零命中场景,12-3 族;四种失效形态见 acceptance 同名节)· **成对判据**(被挡物与被保物成对断言,10-bis 范本)· **消费侧反查**(列「谁读这个字段」清单每点一判据,第 10 条第四长相;射程侧=13-bis)。四形态详情各在括注指到的条目;acceptance 卡有同名速查节,验收侧同用。**⭐ 取值来源通则**:合格的数字可以来自不合格的地方——判据连取值来源一起写死(自跑/同一探针/同一次会话;mock 的取值来源同理),详见 acceptance 卡四形态节。

### 10-bis. 收敛/收缩类片的反事实,值得固化为回归断言就固化(2026-08-14,R4 收敛片范本)

跑一次反事实证明"没挡错"只保住这一次;**把反事实写成回归断言,「为挡 A 顺手挡 B」的风险从此由测试永久值守,不靠下一个人记得**。范本:`c9b42e1` 收敛 weight/通过率时,同片新增 `assertNotIn("weight")`+`assertIn("level")`+`assertTrue(level_distribution)`——被挡物与被保物成对断言。写收敛类 prompt 时把这条列为交付要求,不只列为验证动作。

**守护守语义,不守形态(2026-08-18 方案窗口第十任裁)**:**行为可断言的一律行为断言;源码文本断言仅限运行时不可区分的场景并注明理由**(合法先例=qr_data 条:share_url 与 qr_data 运行时同值,钉「取的是契约字段」只有源码断言做得到——机制复用表该行明写「不是弱化替代品而是唯一有效手段」,那才是该用它的地方)。反例样本:守护正则钉死 api.ts 抛错**表达式字面量**(内容锚=throw Object.assign(new Error(message), { detail }) 的 match 断言,⛔ 行号——该文件一日三改行号无稳定真值),后续片要给该 Error 加 status 字段又不能撞守护,写出「try 里抛、catch 里补 status 再抛」的绕行结构——**代码变形不是因为需求,是因为守护锁了形态**。同族并案片「守护断言形态收口」已立(改行为断言+还原绕行结构)。

⭐ **头注纪律(2026-08-15 生产方式层「当下可判」件②,创始人批)**:凡为守某条裁定/红线固化的回归断言,测试文件头(或用例 docstring)注一行 `# 守护: <裁定编号或R编号>`——补「测试→裁定」的反向追溯:将来改判那条裁定时,能一条 grep 查到哪些测试要跟着动,而不是全量猜。写 prompt 时把这半句并进交付要求;扫描器后配,纪律先行(事故驱动原则:先低成本立规,配套工具等需求投票)。

### 11. 写下游片的 prompt,数据源要核**上游片实际交付了什么**,不能读上游片的设计

> ⭐ **11-bis(2026-08-14 补):「复用既有 X」核到存在只是第一步,还要核 X 在本片场景下前置条件成立。** 样本:重选升级微片——派工窗口核过 `get_assignment_candidates` 存在且参数齐(`excluded_merchant_ids` 都有)即放行,开发方实测才发现它依赖需求期望时间与(到场类)城市前置,而**转单发生在服务中订单上,那些前置未必成立** ⇒ 机制存在、本场景不可用,片被迫停车。**「存在」与「可用」之间隔着一整套前置——核的人要把本片的典型输入喂给 X 走一遍,不是看到函数签名就算数。**(这次是开发方的停车接住了派工窗口。)
>
> ⭐ **11-bis 第二样本(2026-08-14 补):「列可写」≠「行可改」——schema 层与模型钩子层是两道前置。** 同片第三次停车:v2 实测「status 是变长字符串列 ⇒ 加新值零迁移」写进总表,v3 实测发现 `Reassignment` 模型 `before_update`/`before_delete` 钩子一律拒改(只追加,回归测试在案)⇒ 列层面成立的结论被行层面推翻,而那条正是 v3 prompt 的实现前提。**核「能不能写」要真写一行试,schema 说可以不算数——账本族表(ledger/reassignment/order_messages)默认都有只追加钩子,碰它们先想到这层。**

> ⭐ **11-bis 第三样本(2026-08-14):它也发作在台账销账动作上——只核载体,不核使用点。** `PayoutAccount` 外键挂 `user_id`(通用化容器的标志)足以让人写下"收款主体通用化已完成",而 `git grep` 使用点只有 partner 两处、`advisors.py` 零引用 ⇒ 顾问侧根本没接。**"通用化的容器建好了"≠"通用化完成了";销账前核使用点,与写 prompt 前核前置是同一动作。**(dispatch 第十一任自己拦下的,前三处"登记待办实际已完成"的惯性差点让第四处销错方向。)

**样本**(2026-08-13,派工窗口写 `双形态-1b` prompt 时撞见):方案窗口 18:3x 改了《顾问双形态界面设计》§四,**拆出「界面状态」独立一列**,并给 1b 定了硬约束「界面状态非 ✅ 的域一律只渲染锁定预览、绝不给可点入口」。

**但 1a 已经在 17:1x 交付了。** 派工窗口没有照着设计写 1b,而是先核了 1a **实际合入**的接口:

```
git show 4d1b335 -- app/routers/advisors.py
→ domain_lights 每项 = {"domain","unlocks_at","mechanism_ready","unlocks_next"}
→ ⛔ 没有「界面状态」对应字段
```

⇒ 若照设计写,1b 只有两条路,**都会出事**:①按 `mechanism_ready` 给入口 ⇒ `案头视图` 那行 `mechanism_ready=true` 而界面(双形态-2)根本没开发 ⇒ **R42 假门**;②前端硬编码"案头视图除外" ⇒ **逐个域特判**,以后新增域必漏。

⇒ 处置:先立 A 轨微片补 `ui_ready` 字段,**1b 排在它之后**。

**⚠️ 为什么不能"先按约定字段写、等微片补上"**(方案窗口的判断,理由比"保守"硬得多):1b 若按一个尚不存在的 `ui_ready` 写,Codex **自测时那个字段是 `undefined`**,而 `undefined` 在 JS 里 **falsy** ⇒ **所有域都退化成「锁定预览」,全绿通过、看起来完全正确** ⇒ **判据对"这个字段是否真的存在"零分辨力**。这与第 10 条是同一个病。

⚠️ **射程补充(2026-08-13 当天第二例逼出来的)**:上面写的是"上游**片**",但**上游也可能是设计文档本身**。

**样本**:`商会生命周期治理` 的 prompt 抄了设计 §六 那句「无未结外溢/未决评审(**与商会-5 自治门槛用同一判据,复用不新造**)」,**而那个判据根本不存在** —— `git grep -lni "spillover\|外溢\|autonomy\|自治" main -- app/` 全部零命中,设计只把它列为"建议门槛"、尚未工程化。⇒ Codex 因"复用不新造"与"卡点必须有"无法同时满足而停车。

> **凡 prompt 里出现「复用既有 X」「与 Y 用同一判据」「沿用既有 Z」这类措辞,X / Y / Z 都必须当场 `grep` 证明存在**,不论它来自上游片、索引表还是设计文档。
> **发车前检查加一步**:把本片设计里所有"复用既有 X"的 X 逐个 grep 一遍。

📌 **配套的上游条(方案窗口给自己立的)**:**设计文档里写"复用既有 X"之前,X 必须当场核实存在;核不出来就写成"需新建"或"待核",⛔ 不许写成既有资产。** ⇒ **一个不存在的「既有机制」,比一个明说要新建的机制危险得多** —— 后者会被排期,前者会被当成零成本。

⚠️ **还有一个更隐蔽的变体:结论对、理由错。** 同一片里,dispatch 判"该卡点不做"是对的,但理由写成了"评审后延 ⇒ 守护对象为空";方案窗口实测纠正:**争议/仲裁流程现在就在跑**(`orders.py:1477` 升级、`:1538` 平台仲裁、`OrderStatus.DISPUTED` 全在),而 `order_runbook.py` 的 `TERMINAL_STATUSES = {COMPLETED, CLOSED, CANCELLED, REJECTED}` **不含 `DISPUTED`** ⇒ **争议订单就是"在途订单",已被结清清单第 1 条完整覆盖**。⇒ **正确理由是"已被另一条覆盖",不是"对象为空"。**

> **为什么这个差别必须纠正**:按"对象为空"理解,补的人将来会**补一条完整的新判据**(与第 1 条重复实现,且两条判据可能不一致);按"已被覆盖"理解,只需补**独有的那部分**。⇒ **写进交付报告的理由会指导将来的实现,理由错了,结论对也会长出错误的后续。**

**通则(一对,缺一条缺口仍会产生)**:

> **下游**:写下游片的 prompt 时,**数据源要核上游片实际交付了什么**(`git show <上游commit> -- <文件>`),**不能读上游片的设计文档** —— 设计是意图,接口才是事实,两者之间随时可能岔开。
> **上游**:**改设计文档时,必须检查该改动是否影响已交付的实现**;影响就当场登记校正片,**不要等下游撞上**。
> **横向**:**交接包、总表行、验收建议里的"射程判据"只提供验证覆盖与线索,⛔ 不是产品需求**——产品行为一律回读设计本体(实撞 2026-08-14 夜:1b prompt 把交接包那条「九个 ui_ready=false 域逐域列出」当成渲染要求写死,与设计 §〇之3 正面冲突致方向性打回;写 prompt 的人核了字段存在,**没核设计说这个字段该怎么用**)。
> ⭐ **为什么必须回读(同案的传播学)**:那颗雷走了**四跳**——设计歧义句 → 交接包射程判据 → prompt → Codex 实现,**每一跳都忠实转述、每一跳都"有据可依",最后长出违反红线的界面**。⇒ **"忠实转述"本身不构成安全,引用链越长越像安全**——恰恰因为每跳都有出处,没人觉得需要回读;中间任何一跳抽查一次源头,链就断了。⚠️ 对偶的上游责任同案坐实:**约束语句要把"谁允许出现"与"出现者长什么样"分开成两句**——"非 ✅ 域一律只渲染锁定预览"这种写法,形态约束与全集指令在中文里同形,读错的人是无辜的。

⚠️ **只有下游那条,缺口仍会产生,只是被下游接住;两条都有,缺口在源头就被登记。** 本次是被接住的 —— **能接住是好事,但它本不该需要被接住。**

📌 **这是"以为有、实际没有"在本项目的第五例,也是唯一一例发生在「设计与实现之间」**(前四例:代码里的字段语义重载 ×2、设计文档表内一列表达两件事、前端映射表混装两个域)⇒ **同一个病能在四个不同层面发作。**

### 11-ter. 计数交叉要换计数单位——交叉验证本身可以是假的(2026-08-14,验收方提出、方案窗口立卡)

**两种探针交叉,若共用同一个计数单位,同一盲区被复制两遍,交叉零分辨力。** 判据句:交叉验证的两路必须至少在**计数单位或匹配机制之一**上独立;只换匹配串不换单位=假交叉。

样本:空态块收口片(`7b2765b`)prompt 明写"两种探针交叉"、开发方也照做,但两路都是 `rg -n`+`wc -l` **按行计**——`merchants/dashboard/page.tsx` 一行里写了 2 个空 actions,双双数成 1,处数 17 报成 16。失败不在执行,在判据设计:**换单位的办法=一路按行、一路按出现次数(`rg -o|wc -l`)或 AST/结构化计数**。

### 12. 任何"零命中"结论,先在更大范围复跑一次再下结论

**这是第 10 条"被测对象是空的"的近亲,但更隐蔽:被测对象不空,是探针坏了。**

**一天之内四个样本,分属三个窗口 —— 没有一个是粗心,全都是探针形态选错**:

| 探针 | 得出的零命中结论 | 实际 |
|---|---|---|
| `grep 'scope_unclear' frontend/` 找理由码映射表 | "全站无中文映射表" | **该值本身不属于任何值域**(幽灵值)⇒ **拿幽灵值当探针,当然什么都搜不到**;实有 5 套 `Literal` + 2 张中文表 |
| `git grep probation -- app/routers/merchants.py` | "商家侧零露出" | 实现在 `chamber_relationship.py` ⇒ **按文件名推断位置** |
| `git show main:app/models/service_slot.py` | "时间片零载体" | `ServiceSlot` 定义在 **`merchant.py:59`** |
| `git grep "class .*Dispute" -- app/models/` | "评审成立可能没有载体" | 争议是**挂在 `Order` 上的字段族**,不是独立表 ⇒ **按预期形态搜索** |

⇒ **四次共同形态:探针形态选错时,「零命中」与「真没有」输出一模一样。**

**做法三选一(至少做一条)**:
1. **扩大范围复跑** —— 单文件 → 整个 `app/`(这正是拦住第 2 例的动作);
2. **换探针形态** —— 按类名找不到,就按表名 / 字段名 / 调用点找;
3. ⭐ **先证明探针本身有效** —— **用一个你确知存在的值试一次,搜得到才信这个探针**。

**12-bis. 「设计没写 X」也是零命中结论,判之前先按 X 的关键词全知识库 grep 一遍**(2026-08-17 dispatch 第十九任实撞后立,授权-2 批入):只读片级设计单源就判「设计没写审核者」,而「内容审核队列」在角色主页策划的两处早已写明 ⇒ 白开一个裁定缺口。**知识库比代码更容易漏**:一件事的机制、形态、界面、落位常分散在三四份文档,片级单源天然只覆盖其一。⇒ 通则:**对知识库下任何「没写/没有/缺」结论前,`grep -rn "<关键词>" 知识库/` 复跑一次**;开缺口本身不是错,漏核才是。

**12-ter. 一条报警被判为误报后,它遮住的同类报警你也看不见——工具修好必须回头复跑受影响产物**(2026-08-18 dispatch 二十二任实撞后立):prompt-lint 5 项编号误报修复后复跑同一份 prompt,**立刻暴露 2 处真裸文件名**——此前它们混在误报堆里被一起「按误报处置」了。⇒ 通则:凡把某类报警整体判为误报绕过的,**工具修复后对绕过期间的全部产物复跑一遍**;「误报」判定的有效期到工具修好为止,⛔ 不自动延续。

**12-quater. 结论对不等于依据对,依据错时结论仍可能对——两者分别核**(2026-08-19 方案窗口第十任核准措辞,待办 fallback 案):否掉错误依据时 **⛔ 连带否掉结论,核完差集再定**。样本:prompt 指认「disputes 缺 sectionMeta 条目走 fallback 跳首页」——依据错(disputes 有条目,开发方纠正对),**结论对**(验收方比对两侧 key 全集:后端 22 键 vs 前端 21 键,差集那一键正是跳首页的真缺陷)。⚠️ 与 12 族其他形态的区别在后果:那些是结论也错,查出即否;**本形态里错误的路径通向真实缺陷——没人核全集时,真缺陷会跟着错误指认一起被否掉**,纠正者完全正确的纠正本身就是掩埋动作。配套:核这类事一律**比对两侧全集取差集,⛔ 逐个目测**(目测正是依据出错的方式)。

**12-quinquies. 判「某功能/某检查存不存在」一律读定义处,⛔ 从输出反推**(2026-08-19 dispatch 第三十四任自撞并自析给措辞,中继 relay 第二任核库落卡):**输出只能证明「这次跑到了」,⛔ 证明「有没有这条」**——短路(`cond && print`)、条件分支、早返回,任何一个都能让**存在的功能在输出里隐形**,而「这项检查不存在」与「这项检查跑了且通过了」**在输出上完全同形**。样本:为判 `laixin-lane doctor` 有无常驻循环代龄比对,grep 其**输出**零命中,据此判「缺代龄比对」并提议登记机制缺口;实际 `cmd_doctor` 就在调 `loop_stale wd-loop`/`loop_stale ev-loop`,函数定义在同一文件(`bin/laixin-lane:1334`),且**正是为此专门立的**(#20⑥),写法 `loop_stale X && wrn "…"` 短路 ⇒ 那次零命中的正确含义是「**检查跑了、通过了**」。⚠️ **隐蔽处在于同一轮里他做对过一次**:为核 commit 改动面**去读了源码**(`git show --stat`),却在判「有没有这项检查」时**改用输出去猜** ⇒ **不是不知道该读源码,是没意识到这也是一个「存不存在」问题**。**落地动作(触发条件写死,因为知识不构成触发)**:凡要下 **「X 不存在 / 没有 X / 缺 X」** 类结论——不论 X 是字段、端点、机制、还是**一项检查**——**一律打开定义处**(源码/配置本体/表结构),⛔ 以任何形式的运行输出为准。⭐ **配套触发点(同轮自析)**:**当你能把某缺口的完整判据顺畅地写出来时,先 grep 一次那个判据是不是已经在跑**——他提议的判据是「`ps -o lstart` 比 `git log -1 --format=%cd`」,而 `loop_stale` 干的就是这件事;**一个人能把某功能的实现细节顺畅地写成需求,恰恰说明这功能理所当然到了它很可能已经存在的程度**。**与既有条目的关系**:12 族防「探针形态选错 ⇒ 零命中与真没有同形」,本条是它在**被查对象是一段逻辑而非一个符号**时的形态——**符号只要存在就能被 grep 到,逻辑却可以存在而不执行**;与台账八律第 4 律「分桶判据读源码,⛔ 不从行为反推」是同一句话的两个场景(那条写给**写台账**的人,本条写给**做判断**的人)。

**12-sexies. 零命中**是真的**时,先问一句:是「漏」还是「被明令禁止」**(2026-08-24 16:59:12 立,dispatch 第六十四任实撞;方案窗口第二十七任当轮确认「差点让我去补一个违 R30 的词」):第 12 条上半治「探针坏了、零命中是假的」,**本条治另一半——探针没坏、范围也对、零命中是真的,错的是你对这个零的解读**。**实撞**:按裁定池「商会-16」字面的「落平台账本**虚拟余额**」去 grep 供给侧词汇表,`虚拟余额`／`账本余额`／`商会余额` **全 0 命中**,差一步就报「缺余额面词,请方案窗口补」;换成**枚举整节**(⛔ 逐词猜)才看到该词族(`§三补·商会经营域首片 D7`)**明令禁用「余额」「账户」「单用资金」三词**,逐字理由「三词都暗示商会持有可支配款项,违 R30/R25」,它甚至自注了那个零——「全表 `余额` 0 处(**禁它是免费的**)」。🔑 **必须成规的理由**:「被明令禁止」与「遗漏」在 grep 输出里**完全同形**(都是 0、都不带解释),而**处置方向相反**(遗漏必须补／禁止绝不能补);⭐ 最毒的一层——**照「遗漏」处置会驱动上游去补一个正面违反红线的词**,而**报缺口这个动作看起来完全尽责**,没有任何信号提示你正在请人违规。**动作**:对**词表／规则表／判据表**下「缺 X」结论前,**先枚举 X 所属那一节的全貌**,读它的**约束列与节尾注**——禁用词往往就写在那里,且常常连「为什么是 0」都替你写好了。⚠️ **⛔ 逐词猜同义词**:我猜了三个都是 0,**反而更确信了错的结论**——猜得越多,假结论越硬。📌 **与第 12 条上半的分工**:上半问「这个零**可信**吗」(探针有效性),本条问「这个零**是什么意思**」(零的语义)——**两问都过,结论才成立**。

### 13. 单点缺陷到手,先问"同一意图还有几处实现" —— 不一致处就是下一个缺口

**一天之内三例,分属三个载体,同一个病:同一意图被多处独立实现、彼此不知道对方存在,不一致处即缺口。**

| 意图 | 散装形态 | 缺口出现处 |
|---|---|---|
| "必填文本必须有内容" | 部分 router 用值处 `strip()` + `work_order.py` 专门 validator + 其余零处理 | `ReviewDecision.note` 纯空白过校验(`min_length=1` 全站 76 处) |
| "Select 选中后显示人话" | 只有 `standardize:152` 带 children,其余 9 处裸奔 | 7 个页面触发器直出英文码 / UUID |
| "时间输出带时区" | DB naive default 与 Python aware 写入混用,同一条记录两字段两种基准 | 全站时间恒偏 +8h |

**做法两条**:
1. **定性时**:收到单点缺陷报告,先 grep 同一意图的**全部实现形态**并列表——问的是"这是一处笔误,还是一族散装";答案决定开的是补丁片还是收口片,也决定验收射程;
2. **修复时**:修法落**共用层**,⛔ 不逐处打补丁——逐处补完的那一刻,就制造了"下一处新增时的又一个漏网点"。⭐ **已存在的"唯一正确处"不是安慰,是证据**:它证明其他处的作者根本不知道有正确写法,靠人记住是防不住复发的。**且收口片必须把这个"唯一正确处"也切到共用层**——否则收口完成那一刻,系统里就有**两种正确写法**,那是下一轮散装的种子(实撞:`work_order.py` 的 validator 是全站唯一正确的空白校验,空白文本收口片被要求连它一起切过来);
3. **数字是快照,不是规格**:登记时数到的处数(如"76 处")会随在飞片合入而变(dispatch 复测同一 grep 已 78)——**prompt 里要求开发方自数并贴命令,⛔ 不照抄登记数字**。

### 13-bis. 改一处数据源的「读法」之前,先列全部读者(消费点)——不论改动多小(2026-08-18 立,dispatch 与方案窗口共判入卡)

与第 13 条是**同一条纪律的读写两面**:13 管「改实现前列全实现」(同一意图几处实现),本条管「改读法前列全读者」(同一数据源几个消费点)。样本(`f4a8818` 服务卡页片):裁定「保障区改词表定稿句 ⛔ 读 refund_policy 字段」,改 prompt 时没问「这字段还有谁在读」⇒ 同一个付款页从卡页入口进显定稿句、从聚合页入口进显后端常量原文——**main 上两处本同源一致,分叉是这片新引入的**。

**⛔ 因为改动小就跳过本条——「prompt 只改几处」正是本条最常被漏的场景**:同一天同一对文件,dispatch 从零写 prompt 时做了全量实测(抓到 join 双实现并写死只接一处),「只改三处」时没做同样检查(漏了)——**差别不在知识在触发条件:「小改动」不触发全量核查的心理开关,所以触发条件必须写在规则里**。与第 10 条第四种长相(判据沿消费侧反查)同族:那条管验收判据,本条管改动射程。

### 13-ter. 拆防线先清点余防(2026-08-18 立,方案窗口第十任裁并给措辞;13 族第三面)

**锚圈射程要列全同域并列物(2026-08-19 中继 pingxia-1a 落卡,授权-2;11B 复盘页 §五-20 转规则,13 族第五面)**:凡用**锚**(某区块/某字段/某组件)圈定 prompt 或设计的射程,**必须列出同一容器内的全部并列元素,并逐个声明动或不动**——⛔ 只写锚本身。样本(b60 打回根因,方案窗口第八任收班登记):设计单锚只圈了「评分」,同容器里并列的**评语框**没被声明 ⇒ 开发方按锚做完,并列物成了射程外的空白,验收打回。**为什么是清点族而不是写法问题**:锚在写的人脑子里边界是清晰的(他看着那个元素),在读的人眼里边界止于字面;**「同域并列」恰恰是最容易被默认包含、也最容易被默认排除的那一类**——两种默认都不会报错,直到交付才发现两边理解相反。逐个 declare 的成本是一行,不 declare 的成本是一轮打回。

**新增/改变状态前先列全「谁会扫到它」(2026-08-19 中继 pingxia-1a 落卡,授权-2;11B 复盘页 §三之二-14 转规则,13 族第六面)**:凡片会**新增一个状态值、或让既有状态出现在新场景**,prompt 方发车前逐一过一遍**全局扫描型机制**——patrol 与各类巡检 · 托管状态机 · 通知与待办生成 · 定时任务 · 聚合统计,问「**本片的新状态会被它们怎么处理**」,并把答案写进 prompt(该被它捞走的/该被它跳过的,各自给判据)。样本(patrol 吞溢出单):新状态落进了一个谁也没想起来的巡检的射程里,巡检按旧语义把它捞走处理掉,**验收拦住了但已是一轮整改**。⚠️ 这类事故的特征是**两边代码各自都对**——新片按设计写对了,巡检按它写的那天的语义也对;错的是「没有人在这两者之间站过」。⇒ 清单本身要有落盘处(机制复用表「全局扫描型机制」节),⛔ 靠每任 prompt 方现回忆:**能被回忆起来的机制,恰恰是不会出事的那些。**

### 14. 引用红线时,守护对象逐字回原文核,⛔ 不凭语义相近代入字段名

**样本(双形态-2,2026-08-14)**:prompt §七.7 要求「核 `review_opinion` 零命中」,而 **R21 原文守的是 `review_note`**。两个字段语义相近(都是评审产出),披露面却相反:`review_opinion` 对消费者是**有意披露**(collab 经 `fulfillment.review_outcome.summary` 包装、`/api/orders/{id}` 返回裸键、消费者订单页故意渲染)⇒ 按字面判据「零命中」**不可能成立**;按 R21 本体(`review_note`)则通过。

**这条的危险不在判据不通过,在它可能"被修到通过"**:开发方若为凑绿去动 `review_opinion` 的披露,会**真的删掉一处有意为之的消费者可见信息**——与第 8 条「消灭 `|| x` 反而丢信息」同一伤害形态,发作点不同:**第 8 条发作在"从代码形态推断数据",本条发作在"引用红线"这个动作上**——而红线引用恰恰是 prompt 里最像"照抄就安全"的部分,没人会质疑一条自以为在照抄的红线。

**通则**:
1. prompt 里每引用一条红线编号,**当场翻开红线清单该行,把守护对象(字段/端点/页面)逐字抄进判据**,⛔ 禁止凭记忆或语义相近写字段名;
2. **判据写成「R21(守 `review_note`)零命中」这种自带原文的形态**——读的人一眼能核引用与判据是否同一对象;
3. 与第 6 条(转述断言也要核)同族但更隐蔽:**转述至少看起来是转述,错引的红线看起来是原文。**


**14 的另一半:引不全(2026-08-18 方案窗口第十任裁;本条管引错,这半管引对了但只引主句)**:引用红线做射程判断时,附「**相关扩展注/边界注已核,结论=X**」;该行无相关注也要显式说一句——⛔ 裸主句当全部(**编号=整行**,权威规则在红线清单表头:主句只是名字,整行才是法条)。⚠️ **两者隐蔽度不同**:引错会在判据不过时暴露,**引不全一路绿灯**——漏掉的那半句恰恰是用来扩大射程的。判例(分槽片实撞):报告引 R10 只录主句、漏「一切枚举直出同属实质范围」扩展注——所录文字无误引,但**同一个漏引,在这片里是报告瑕疵,在贡献事件裁剪片里就是「我判自己不在射程内」**(那片的立片依据正是这条扩展注)。📌 规则本体落在红线清单表头而非本卡,是有意的:**射程判断必然要打开清单查编号,本体是必经之路**;与「事实表刷新说明只写在表头上没人看到」结论相反相成——**规则写在本体还是流程清单,取决于用它的人是否必然经过本体**,两件同晚发生结论相反,不是矛盾是同一判据的两次应用。

### 14-bis. 设计硬约束用固定句式(约束句模板,M6)

**写进设计或 prompt 的硬约束,一律拆成三句填空,⛔ 不许合并成一句**:

> **允许出现者 = X**(谁/什么条件下才出现)
> **出现者形态 = Y**(出现时长什么样/什么行为)
> **反例 = Z**(违反时的具体样子,可实测)

**样本(一夜三例,同一病:一句话同时承载"谁允许出现"与"出现者什么样",中文里两种读法完全同形)**:
- 设计 §四:79「界面状态非 ✅ 的域一律只渲染锁定预览」被读成「9 个域都渲染锁定预览」⇒ 1b 方向性打回,歧义句四跳传播三处落点;
- P4「带归因参数就显示」条件写半截 ⇒ 拿他人 ref 也显示;
- 「dissolving 不得建新卡」未写存量卡形态 ⇒ 存量 draft 提交送审绕行。

**判据**:约束句写完自问——"X 之外的东西读者知道它**根本不出现**吗?Y 是对 X 的形态约束还是对全集的渲染指令,分得开吗?Z 能直接变成反事实测试吗?"三问有一个含糊就重写。

### 15. 照台账登记写 prompt 之前,先实测那个缺陷/状态还存不存在

**同一天两个方向各一个样本**:
- **「说待发,实际已合」**:排队节 87% 行(56 行中 49 行)是已发车/已合入残留,派工窗口一轮选片连撞三次无谓调查,方案窗口也引其一荐了已合入的「燃料」;
- **「说缺陷在,实际已修一半」**:页脚片发车前实测,总表登记的两件缺陷,第①件已被 `eee0626` 顺带修掉(内联 `[--foreground:…]` 覆盖恰好罩住 `SiteFooter`),第②件数值已从 2.49 漂到 ≈4.02。

**共同病:台账的陈述性状态不随事实更新,而读它的每一方都把它当事实。** 登记是快照,不是现状;上游片随时可能顺带改变它描述的世界。

**通则**:凡 prompt 的立项理由或判据引自台账登记(缺陷行/缺口节/排队行),**发车前把该登记描述的现象重新实测一遍**——还在,贴当轮取值;不在或已变形,先改台账再决定片还成不成立。⛔ 「登记着」不是「存在着」的证据,正如「排着队」不是「没做过」的证据。

### 16. 凡新增待办/通知/入口,必须同时写明「接收者用什么动作完成它」

**样本(2026-08-14,重选微片二次停车)**:prompt 把「建顾问补齐待办」的机制形态写得很全(拉取式 section+前端两处配置防英文 key 死链),**唯独没写顾问点开待办之后用什么完成它**——实测该待办没有任何可完成的既有去路。写 prompt 的人自己要求核 R42,却没把 R42 应用到自己新增的待办上。

**通则**:新增待办/通知/入口时,prompt 必须把完成动作**列进射程**,或明确写「已存在,在 <位置>」(带实测证据)。既有假门条目守的是「界面有按钮但后端没有」;这条守的是它的镜像——**系统给人派了活,但没给他干活的地方**。⭐ 附正面样本:lane-a 同轮排除了「把服务中订单放回标准化路径」的绕法(会绕过锁版本承诺)——**替上游排除一条看起来可行的绕法,与报告缺口本身同等值钱**。
