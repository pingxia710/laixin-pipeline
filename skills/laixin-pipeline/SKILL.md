# laixin开发流水线(编排卡)

> 权威流程在 [[来信平台-开发协作流程]]"laixin开发流水线"节,本卡只给操作程序。
> 铁律一:**自动化只搬消息,不动闸门**——发车位纪律、验收七步(laixin-acceptance)、基点纪律原样执行。
> 铁律二:**状态永远在知识库,不在窗口记忆里**——执行总表(片级)+看板(事件流)随做随写,任何窗口随时可被换掉。
> 铁律三(2026-08-13 事故后立):**验收结论里的每个数字、每处代码引用,必须能在紧邻的真实工具返回中逐字找到**;记不起对应返回的,重新执行工具,不得凭印象书写。

## 0. 先确认你是哪个窗口

2026-08-13 起,原"执行窗口"按职能拆为两个:

| 你是 | 你做 | 你**不**做 |
|---|---|---|
| **派工窗口** | 写 prompt、`laixin-lane` 派工、监听交付与轨道状态、交接给验收窗口、收回执后合并、更新执行总表 | **不验收**(不许自己验自己派的片) |
| **验收窗口** | 只做独立验收:复现证据、跑全量、browser-harness 走查、rebase 后复跑、写验收记录、给结论 | **不写 prompt、不碰 lane、不合并** |

不确定时问创始人或方案窗口,**不要两个都干**——那就是拆窗口前的旧形态。

> 🔧 **遇到工具/流水线问题(11B),或 11C 工具侧的活?** —— 它是**第四条开发轨**,由 **`laixin:dispatch`(管 11B 的那个派工窗口)**按件拉起
> (⚠️ **`dispatch-11c` 在工具层被硬禁 `tool-up`,这是对的 ⛔ 开口子**——它的工具需求走归口点名给 11B 归口):
> `git -C ~/Developer/laixin-pipeline worktree add <路径> main` → `laixin-lane tool-up <件名> --prompt <开发prompt.md> --dir <路径>`
> (**引擎 codex 默认 / claude 第二**,`--engine codex|claude`;codex 与开发轨同源吃全局模型默认、用量档由 `laixin-lane codex-tier normal|fast|status` 统一控制（默认普通）,claude 钉模型+工具层禁令;**派工窗口写 prompt**;开分支 ⛔ 提交 main;交付 `记录/11B工具件-<件名>-报告.md` 末行【工具件完成】⇒ events 投指针;件毕 `laixin-lane tool-down <件名>`)。
> **写 prompt 前先读角色卡**(射程与边界):`~/Obsidian/项目入口/laixin开发流水线/知识库/wiki/11B-11C开发维护角色卡.md`。
> ⚠️ 该线**只维护 11B/11C** ⛔ 产品代码;⛔ 起验收窗 ⛔ 进 M1 台账。

## 循环

**1. 派工(每轨一次只飞一片;每片全新上下文)**
- 🔁 **写 prompt 动线(2026-08-23 创始人拍;组织原则=单任务质量最高,派工窗口只做组织协调)**:prompt 起草**不再由你亲写**——`laixin-lane prompt-up <片名> --pack <底稿>` 点名一次性写单窗按 kickoff 卡起草(一件一窗,codex 钉 sol);交稿事件到达后你走 **Gate2 收稿把关**(lint 独立复跑 ⛔ 采信自报 · 抽核实测表 2-3 条 · **基点/占号校准与扫存量必须在发车时刻做** ⛔ 采信起草时读数)→ kb-commit → 先登记后发车 → prompt-down 回收;缺料停车件转方案窗口 ⛔ 自裁。kickoff 检查项**一项不删**,只按「起草时/发车时」重新分配执行人(kickoff 卡「归属两半」节);细则与失败面=4-开发层/来信平台-写prompt动线-方案稿-20260823.md。下文各条 prompt 纪律(落盘契约/实测表/枚举写入方)**原样有效**,只是执行人按两半分;
- 核执行总表"进行中"节:该轨有片在飞 → 不发(发车位纪律);
- **判「无片可发」前,先扫总表「⚠️ 已上线缺口」节找「后端已在 main、前端零引用」的条目**(2026-08-17 立,dispatch 十九任样本:排队空转两轮后重扫一次找出 4 条天然纯前端 B 片)——它们是反向假门(能力已承诺、门没装),优先级比新功能硬;缺设计的点名方案窗口/裁定路由细化,⛔ 不自拟射程。**排队节空 ≠ 没活干**,「四个候选都发不了」这类结论只对排队节成立,⛔ 不扩大成对整个知识库成立(与 kickoff 12-bis 同族:窄范围结论不下宽);
  ⚠️⚠️ **但「已上线缺口」节的条目,发片前一律重实测——它与排队节 ready 片不同档**(2026-08-20 02:4x 立,方案窗口第十四任裁「够立」,dispatch 第三十九任同夜第二次撞见后提):
  **病灶**:该节条目是**某次验收的历史快照**,而它记录的缺陷**会被后来的片顺带修掉**——`git log` 里有痕迹,**台账里没有**。⇒ **一条已闭环的缺口,在台账里看起来和三天前完全一样。**
  **当夜样本**:方案窗口据该节点名 `消费者订单页两处既有 R4 越界` 排进 B 轨;dispatch 写 prompt 前先核事实,`git show main:` ref 级实测发现——登记说的两处现在只剩一处、剩下那处在受控 Dialog 内、两个打开点都有 `isConsumer` 门 ⇒ **登记里「无角色门控」那半在 main 现状下不成立**;`git log -S` 一条命令追到是 `4274e41`(08-18 12:50)顺带删的,而登记来源是 08-17 23:2x。
  🔴 **不重实测的代价形态**:开发方会去修一个**不存在的缺陷**,并在交付时**如实报「未复现」**——那时已烧掉一整片的开发加验收成本,而**过程里每一步都合规**,没有任何信号提示前提是假的。
  ⚖️ **重实测的完成判据**:①逐条核登记里点名的**文件与行号**是否仍指向那个东西(行号漂了就换内容锚);②闭环了就 `git log -S'<关键串>' -- <文件>` 追出是哪片修的,按销账写回被引用处;③**自标结论射程** —— 「登记点名的那几处不成立」⛔ 等于「该类问题已清」,后者要按红线原文重新穷举。
  📌 **与「收到请裁件先核该件在库里的当前状态」同族、方向互补**:那条治**消息**过期(库前进了),本条治**台账条目**自身过期(世界前进了,台账没动)。
- **先 `fresh` 再 `send`**——Codex 上下文不跨片,prompt 自包含(权威库直读);
- 🔴 **改 prompt 本体必须先于 send 通知,且 prompt 要提交进 vault git 才算「落盘契约」**(2026-08-20 03:1x 立,dispatch 第三十九任自撞、开发方拒收发现)——**这是「先登记后发车」在 prompt 侧的同一条**:那条防台账滞后,本条防**契约滞后**。
  **样本**:dispatch 收到方案窗口对一个停车件的裁定后,**先 `send` 给开发方、后改 prompt 本体**;开发方收到消息**立刻 `stat` 那个文件**,读到的是旧版(实测 `mtime=02:51:22 size=17880`,不含新增的任务 0),**第二次停车拒收**,原话逐字「**按项目协议,我不能用聊天内容替代未落盘的派工契约**」;它同轮还核出第二条:**该 prompt 在 vault git 里是未跟踪文件,无法确认发车版**。
  ⭐ **两条都对** —— 开发方是那一轮里唯一把顺序做对的一方。⚠️ **⛔ 因为「我已经在聊天里说清楚了」就放宽这条**:聊天内容不是契约,**下一个读这份 prompt 的人(验收方、整改轮的新 codex、接班 dispatch)读到的都是盘上那份**。
  **动作三条**:①裁定/口径变更到手 ⇒ **先改 prompt 本体 → 再 `kb-commit` 提交 → 最后才 `send` 通知**;②`send` 里给出**开发方可自核的三个量**(`stat` 的 mtime 与 size · 提交 hash · 关键串的 `grep` 命中数),并明说「你自己核,不要信我这段文字」;③**⛔ 只带外补发**——历史上还有一次同族形态:口径变更只 `send` 给在飞轨道而 prompt 本体没改,开发方整改时重读 prompt 会**同时读到两个口径**。

- 🔴 **写 prompt 时,凡改「共享键/共享存储/共享出口」的写入侧,先枚举它的全部写入方,再写实测表**(2026-08-20 04:3x 立,验收方提出、dispatch 第三十九任认下自己那一半)——⛔ 只点一处并写「修法就在这一行」。
  **样本**:`付款页微修族` 要修的是 `card-join:` 这把 sessionStorage 键少落一个字段。派工方实测表**只点了 `cards/[id]/card-page-client.tsx` 一处**并逐字写「**修法就在这一行**」;开发方照做,交付后验收方核出 **`aggregate/[id]/aggregate-page-client.tsx` 也写同一把键**、同样没落该字段 ⇒ **本片要修的缺陷在另一条入口路径上原样存续**,J1 在该入口不成立,片被打回。
  ⚖️ **责任分担(验收方判、派工方照收)**:prompt 未枚举第二写入点是**派工方那一半**;而同表标题写了「你仍需自己复核」、第 13 条也要求下「不存在」结论前扩范围 ⇒ **开发方那一半也成立**。**两侧各一半,⛔ 单方面归责。**
  🔑 **为什么这条特别值得写死**:派工方的实测表**本意是省开发方的力**,而「**修法就在这一行**」这种确定性措辞会**直接关闭开发方的搜索动作** —— 越是写得肯定,越是把自己的覆盖面缺口变成对方的执行边界。⇒ **实测表里的每一处「就在这里」,都要先问一句「这个东西还有别的地方吗」**;拿不准就写「**我只核了这一处,你自己扩范围**」。
  **动作**:①共享键/共享出口类改动,prompt 里给出**枚举命令与结果**(如 `grep -rn "card-join:" frontend/src`),⛔ 只给一个行号;②判据里加一条「**守护断言覆盖全部写入方**」,防单点修复;③枚举不全时**明写不全**,别让确定性措辞替开发方做决定。

- **`send` 之后必 `peek` 复核**:见 `Working`/`Explored`/`Read` 才算派工成功;只见提示符=消息被吞,重发;
- **发车前校准占号(机器执法)**:A 轨跑 `laixin-lane next-migration`,B 轨跑 `laixin-lane next-worktree`——未合并分支与未提交文件都占号,main 上 `ls` 看不见(0026/0033 两次实撞);prompt 里写死的号以此为准覆核;
- **先登记后发车(2026-08-13 改,顺序即闸门)**:`send` **之前**先把总表改到位(交付片移入"验收中"、本片登记"进行中"),再 fresh+send——**Codex 的发车前置检查读的就是这张表**,先发后登必留一个读到旧表的窗口期(实撞第三次:lane-a 因台账滞后拒发,三次全对);发车后看板记 `派工 <片名> → lane-<轨>`。

**2. 事件由事件总线投递(2026-08-13 第三轮:你不需要也不要自建 Monitor)**

`laixin-lane dispatch` 起窗时自动带起 `events` 窗口(纯 bash 常驻循环,看门狗会保它活着)。**监听不再随派工窗口死**——这正是 7.8h 停摆的直接机制(监听活在窗口进程里,窗口一换监听就停)。它投递三类:

- **【事件】交付落盘**:直接进你的输入框,含报告路径与末行,下一步通常就是 `verify-from`;
- **【告警】lane ≥6 分钟无变化**(空闲或卡住):自带该轨下一片提示与三选一强制动作(派工/现在写/总表写明),**不得静默**;

**3. 交接给验收窗口(交付到达时)——一片一个,验完即弃**

优先用一步式(解析报告末行取分支与 commit,**防手抄 hash 笔误**,顺带机器校验交付契约与 commit 存在性):

```bash
laixin-lane verify-from "<交付报告绝对路径>" --prompt <prompt绝对路径> --to dispatch
```

或手动全参(报告末行不合契约、需要覆写时):

```bash
laixin-lane verify <片名> \
  --branch <分支> --commit <HEAD commit> \
  --report <交付报告绝对路径> --prompt <prompt绝对路径> \
  --to <你自己的会话名>          # 回执发给谁;不传则它自己 ListAgents 找
```

脚本会:在 tmux `laixin` 会话新开 `verify-<片名>` 窗口 → 起一个**全新 claude**(`--permission-mode auto` + 工具白名单/黑名单)→ 自动过信任与 MCP 提示 → 把五项客观信息派进去。约 15 秒返回。

- 复核:`laixin-lane peek-v <片名> 30`;观看:`laixin-lane attach`;列在跑的:`laixin-lane vlist`;
- 收到回执并合并后:`laixin-lane vdown <片名>` 回收(与 worktree 回收同理,不留残窗);
- 整改重验:先 `vdown` 再 `verify`(同名窗口不重复起);
- **交接后立刻释放主树**:`git -C /Users/pingxia/来信平台 checkout main`——验收窗口走独立验收树,不依赖主树分支;该片 commit 已落地、分支保留,切走不丢;打回时再 checkout 回原分支整改。**不切,"验收中不占发车位"在现场不成立**——台账说不占位、主树看着占位,**Codex 信现场,且它是对的**(2026-08-13 建库路径修复因此连拒两次)。若报 `fatal: 'main' is already used by worktree ...`:**空闲 worktree 占住了分支,先回收它**——回收 worktree 的真实理由是解发车阻塞,不是省磁盘。

⚠️ **git 写操作必须显式 `-C <仓库绝对路径>`,⛔ 依赖 cwd**(2026-08-19 立,三十任实撞):派工窗口**结构性地**同时操作两个 git 仓库(代码库+知识库 vault),台账工作必然把 cwd 带进 vault——实撞形态:校验命令带了 `-C 来信平台`、执行命令没带,`update-ref` 落进 vault 仓,**校验与执行作用在两个不同仓库而在操作者眼里是一套连贯动作**(「两个真相,一个错误」);没出事纯因该 commit 在 vault 不存在被 git 拒写。**校验与执行必须同一个 `-C`**。与「合并前先 `git branch --show-current`」分层:那条防**分支假设**,本条防**仓库假设**。

⚠️ **绝不允许两个派工窗口同时活着**——两个窗口同时动 lane 会把 Codex 上下文搞乱(2026-08-13 实际险些发生,当时靠人工提醒才没撞)。**机器执法方式:派工权锁**。

- 接管派工角色**第一件事** `laixin-lane claim`;此后每次 `send` **自动续期**;
- `dispatch` 起窗时脚本代它认领;别的窗口来 `claim` 会被拒(除非持有者停止动 lane 超 30 分钟,或显式 `--force`);
- 看门狗在"dispatch 已死但派工权被别人新鲜持有"时**不自动重起**,只告警——那说明有人接管了。

> **为什么不用"数 tmux 外的活跃会话"来判**(曾如此实现,已换掉):数量是身份的**不可靠代理**——你开一个窗口只是问问题、和开一个窗口接管派工,在"数量"里长得一模一样。**基线设低会误判罢工,设高会在真撞车时不拦。** 而 `send` 是派工窗口的**定义性行为**:谁在动 lane 谁就是派工窗口 ⇒ **直接测行为,不猜身份。**

⚠️ **跨窗口移交的每条结论,都要附上得出它的那条命令**。2026-08-13 一天内双向各发生一次"把自己的推断当事实移交":①交接窗口把"商会申请审核状态"整个判为缺口,接班窗口核出接口早已返回;②接班窗口把 `categories.clarification_questions` 判为"字段挂错对象",而 `Category` 类恰好定义在 `demand.py` 文件里(按文件名推断会误读),复核后原文正确。**两次都是读代码得出的结论与代码本身之间那层推断,在传递中丢掉了不确定性标记。** 附上命令,接班方就能一秒复核;不附,它要么盲信、要么重查一遍。**接班窗口重验前任判断是应当鼓励的行为,不是不信任。**

⚠️ **交接只传那五项,不得附带你的判断、预期或"应该没问题"**——你写了 prompt,你的预期就是污染源。脚本发的指令模板已经是干净的,**不要手动追加评论**。

**为什么一片一个窗口**:验收是上下文消耗最大、也最容易凭印象书写的环节(2026-08-13 夜间编造事件全部发生在单片验收内部)。一次性窗口把"靠换班纪律压住"变成"结构上无法积累",与 Codex 每片 `fresh` 是同一条纪律。

**4. 交接的同一轮内,立即派该轨下一片**——**合并不是终点,派工才是**。验收期间该轨空闲是事故,不是等待。

**4-bis. 同域微片打包(2026-08-19 落卡,复盘页 #15;dispatch 排片惯例)**:同一文件域的 2-3 个微任务允许并一片(commit-per-task 纪律已支持),减少每片固定成本(发车+验收+合并各一轮);**上限 3,⛔ 跨域打包**——域的判据=改动面同目录同族,拿不准就不并。

# B. 验收窗口

**你由 `laixin-lane verify` 起,一片一个窗口,验完即弃。** 收到派单后:

1. **先重读该片 prompt 与执行总表在飞节,再读交付报告**——不依赖窗口记忆(可能已被压缩);看板记 `验收开始 <片名>`;
2. 按 `laixin-acceptance` 七步独立验收:**全量自己跑、browser-harness 自己走查、报告没提的验证项就是最该亲手跑的**;判据是"全部 passed 且 zero failed",**不是测试数相等**(subTest 计数不稳);
3. **验收隔离**:主树可能被 A 轨 Codex 占用,一律走独立验收 worktree 或 ref 级操作(`commit-tree`/`branch -f`),**禁止在共享工作树 checkout/merge**;
4. 小口子自行修复并在验收记录写明;方向性问题打回;
5. **最后一步必须是:rebase 到当时 main,并在 rebase 后的状态上复跑全量**——"验的就是合的";
6. 回派工窗口(**按验收窗口的引擎二选一**,`LAIXIN_VERIFY_ENGINE`;⛔ 走 relay-msg——回执是**事实**不是讨论,事实类一律落盘+事件总线):claude 引擎 `SendMessage`;codex 引擎(#60① 默认)把回执写进 `<片名>-验收回执.md`,**末行行首**`【验收回执】`,事件总线据此投递派工窗口。两种形态给的内容相同:
   - 通过 → `verify-*` 分支名 · 其 commit · **所基于的 main commit** · 全量结果;
   - 打回 → 逐条可复现的问题清单 + **打回类型(方向性/工程,分类权在你)** + 是否需升级创始人;
7. 在同一份记录文件追加"验收方独立验收结论"节;看板记 `验收通过` 或 `打回`。

**你不自行 `laixin-lane send`**,即使判定打回也经派工窗口转发——两个窗口同时对一条 lane 发消息会造成 Codex 上下文错乱。

**回执发出后你的活就结束了**——不要找新活干,等派工窗口 `vdown` 回收你即可。(历史片的"零命中"结论复核是另派的独立任务,不是你顺手做的事。)

**工具层已给你上的锁**(不必自觉,也绕不过):`git push` / `git merge` / `git reset --hard` / 一切 `laixin-lane send|fresh|up|down` 均被 `--disallowedTools` 硬拒。记看板用 `laixin-lane vlog "..."`(**不要写 `LAIXIN_WINDOW=... laixin-lane log`**——带 env 前缀的命令不匹配白名单,会平白卡一次权限提示)。

## ⚠️ 进程类探针在本环境系统性不可靠(2026-08-19 晚立;当日**九次**同形自撞,四个窗口各中一次以上)

**结论先行:凡探针的匹配串会出现在探针自己的命令行里,它就会自匹配。** `ps` / `pgrep` /
`capture-pane | grep` 全族适用。当日实撞四种形态:

1. **被别人的命令行污染** —— `pgrep -f "laixin-lane wd-loop"` 命中的是 **relay**:#71 扩
   `RELAY_DENY` 时把 `Bash(laixin-lane wd-loop*)` 写进了它的命令行。**一个纯安全加固动作打瞎了
   两个判活探针**。后果两层:看门狗死了 `doctor` 照样报绿;`cmd_watchdog start` 首行 `wd_alive && die`
   ⇒ **看门狗一停就再也起不来**。⇒ 修法=认**解释器行**,前缀 `(^|/)bash ` 同时防 grep 自匹配;
2. **看不见自己** —— **每个 claude 会话跑 `pgrep -f claude` 都缺自己那个 pid**(三方对称实证:
   dispatch / relay / 11B 各缺各的)。⇒ **被怀疑方自测得到的「没问题」零证据力**,该验证必须第三方跑
   (当日 relay 正是据此把污染误判成「没复现」);
3. **等待条件自匹配** —— `until ps | grep -- "-n dispatch"` 杀掉才 3 秒就假"完成"(命中该循环
   自身的命令行);`grep "BU_NAME=\["` 命中的是**自己 prompt 里的 `%s` 占位符**;
4. **未知子命令回落 help** —— `laixin-lane board` **根本不是子命令**,它打印 help 并 exit 1。
   用 `cmd | grep` / `| tail` 读它的人会**把 help 正文当成命令输出**(当日 11B 归口据此判过一条
   「看板没记录」,而记录好好地在看板文件里,同一件事翻了三次)。现已改成先往 **stderr** 打告警。

**⇒ 优先用不含命令行文本的判据**:`tmux list-windows` 枚举 · sock 文件(`/tmp/cc-socks/<pid>.sock`)·

## ⚠️ 请裁消息的取证完备性(2026-08-19 立,dispatch 第三十五任自核后自提,中继 relay 第四任落卡;样本=件① 发布指纹端点请裁)

⇒ 裁定方拿到的是一个**看起来完整、实则被单方面裁剪过的证据集**,而**裁剪本身是隐形的**:裁定方不知道自己没看到什么。

**规矩(一句话成本)**:请裁时列出「**我为这个问题查到的全部明文,含我判为不适用的,并写明我为什么判它不适用**」。
⇒ 把「我的裁剪」从**隐形前提**变成**裁定方可复核的对象**。⛔ 只报冲突项。

⭐ **为什么必须写成规矩而不是靠自觉**:这条**在推对时完全不可见** —— 本次中继推导出的结论与那两条明文**恰好一致**,所以没有任何信号提示证据集被裁剪过;若明文与推导相反,下游会拿着一条与写死约束冲突的裁定去执行,**而请裁方与裁定方都不会发现**。与「结论对≠依据对」同族,但方向相反:那条讲**否依据不连带否结论**,本条讲**结论对不能反推依据全**。

⚖️ **射程边界(落卡人自标)**:本条约束的是**请裁/求裁类消息**(要对方做判断的),⛔ 扩到一切消息——事实同步、状态回执不适用,它们没有「被裁剪的证据集」这个结构。

## ⚠️ 收到请裁/转递件,第一步核该件在库里的当前状态(2026-08-19 晚立;relay 第五任提出、dispatch 第三十六任当轮认领并补出派工窗口半边)

⚖️ **射程边界(落卡人自标)**:本条针对**要你做判断**的件;⛔ 扩到纯事实同步与状态回执(它们不产生「判过头」的后果)。

### ⚠️ 口径消息到达时,当轮扫存量(2026-08-18 立,一次方向性打回后由 dispatch 与方案窗口各认一半责任)

🔴 **扫存量宣布「零命中」前,探针必须先对一个已知阳性跑一次并命中(2026-08-20 方案窗口第十六任裁,授权-2;dispatch 第四十二任实撞后自报、落卡归撞者)**
**条文(裁定原文定形)**:**扫存量宣布「零命中」前,探针必须先对一个已知阳性跑一次并命中(如该片 prompt 必引的自身射程权威);已知阳性不命中 = 探针无效,⛔ 出零命中结论。**
⚖️ **性质=既有「零 X 结论要对照探针」纪律在扫存量动作上的实例化,不是新立法**(裁定判词)。

**实撞样本(2026-08-20,两个探针错误叠加造出一个假的全员零命中)**:
1. `ls -la <dir> | head -6` —— 该目录 `.` 与 `..` 加 4 个文件恰好 6 项,**`head` 的行数上限正好切掉第 4 个文件**,而那个文件正是要找的目标 ⇒ 据此下了「目录里没有这个文件」的结论;换 `find` 探针才看到;
2. 循环里把中文直接跟在变量名后面拼路径(形如 `"prompt/$P开发prompt.md"`)—— **zsh 把中文当成变量名的一部分** ⇒ 变量不存在 ⇒ 路径塌成只剩扩展名 ⇒ 文件不存在;而 `2>/dev/null` 把「文件不存在」的错误吞掉、短路取零又把它变成 0 ⇒ **五份 prompt 全员零命中,全是假的**。真实结果是其中两份各 1 命中,**且其中一份是当时正在验收的片、它的第一份射程权威就是那份变更材料**。

⭐ **为什么必须成规、⛔ 靠「写命令仔细点」**:**假零命中与真零命中在看板上长得一模一样** —— 扫存量的产出物就是「零命中」那一句结论,而那句话不携带任何关于探针是否有效的信息。本次回头复核的触发点是「首页片却不引首页设计要点,反常」这个**直觉**,而**直觉不是判据**。
📌 **两条附带教训(与本条同族,写给下一个人)**:①`head` 截断会让「不存在」与「被切掉」同形;②`2>/dev/null` 会让「文件不存在」与「零命中」同形 —— 后者正是本卡「⛔ 无脑 `2>&1 |`」那条在扫存量侧的形态。

## ⚠️ 采集前断言当前标签页 URL——端口专属与浏览器专属都挡不住 daemon 串台(2026-08-17 新增,同日两验收方独立实撞)

「专属实例会被 daemon 复用架空」(验收方原话):漂的不是端口也不是浏览器进程,是 **daemon 的标签归属**——`ensure_daemon()` 会忽略 `BU_CDP_URL` 复用别人的 daemon,标签被切到并行验收窗口的页面上。两个当日样本:①通知片验收方标签被切到 `127.0.0.1:3246`,首次采集作废;②主页-3 验收方已起专属 headless(9347+独立 profile),daemon 仍被安全片窗口(3178)复用,一次测量跑在对方页面(h1 数=0)。**规矩(硬要求,⛔ 起了专属端口/专属浏览器也不豁免)**:每次采集/测量前**先断言当前标签页 URL 等于预期**(形如 `ASSERT_URL: http://localhost:<你的端口>/<路径>`),断言失败即中止采集重连,⛔ 不带着未断言的读数下任何结论——两次事故都是靠这条拦下的。

**机制层加固(2026-08-17 当晚实施并升级,`ebe6268` 起)**:起窗自动注入**成对**的 `BU_NAME`(verify=`v<cksum>` 短名 / dispatch / lane-a·b)与 `BU_CDP_URL`(**端口段创始人裁定:9230 往上整段归流水线**——dispatch=9230,lane-a/b=9231/9232,verify=9300-9999 按窗口名派生)——**每个窗口一条专属 CDP 通道**(创始人原话),daemon 按名单例、端口预分配,窗口 ⛔ 自挑端口 ⛔ 连共享 Chrome;端口无人监听时 harness 报错是预期 fail-closed。⚠️ **未经两个并发 verify 窗口实测确认前,URL 断言纪律仍是主防线 ⛔ 不撤**。

**Claude 验收窗口 CDP 走查操作段(照抄即用;Codex 侧已熟不需此段)**:

```bash
# 1) 通道是预分配的,先看自己的:
echo "$BU_NAME $BU_CDP_URL"          # 端口取 URL 末段
PORT="${BU_CDP_URL##*:}"
# 2) 两态(2026-08-20 立):端口已监听=派工侧预起的常驻实例已就位 ⇒ 直接用,⛔ 自起、⛔ 第 4 步 pkill
#    (pkill 会打掉派工方的常驻实例=#42 vdown/cdp_sweep 冲突的收方侧);无监听才自起。
SELF_STARTED=""
if curl -s "http://127.0.0.1:$PORT/json/version" >/dev/null 2>&1; then
  : # 常驻实例已在,直接进第 3 步
else
  # 🔴 自起必须 nohup + disown,⛔ 裸 `&`——裸 & 起的 Chrome 随本命令会话被收走(#42,b86 开工即停车 · 11B 探针原样重现)。
  nohup "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
    --headless=new --remote-debugging-port="$PORT" \
    --user-data-dir="$(mktemp -d)" --no-first-run about:blank >/dev/null 2>&1 &
  disown; SELF_STARTED=1
  sleep 2 && curl -s "http://127.0.0.1:$PORT/json/version" | head -1   # 有 JSON 回显=通道就绪
  # ⚠️ 无回显就是没起成,⛔ 往下走也 ⛔ 判「环境坏/变量为空」——回到本分支重起一次。
fi
# 3) browser-harness 自动读环境里的 BU_NAME/BU_CDP_URL,直接用:
browser-harness <<'PY'
new_tab("http://localhost:<你的应用端口>/<路径>")
wait_for_load()
print(page_info())   # 采集前先断言 URL(上节硬规则)
PY
# 4) 验收收尾:仅当本段自起时才杀,别留孤儿进程(创始人:用完要关);走「已监听」那支的 ⛔ pkill(那是别人的常驻实例):
[ -n "$SELF_STARTED" ] && pkill -f "remote-debugging-port=$PORT"
```

`vdown`/`down`/`fresh`/`halt` 回收窗口时会**机器兜底清扫同端口的 headless**(`cdp_sweep`)——兜底存在不豁免第 4 步,自己关是本分。

⚠️ **本机没有 `setsid`——想让进程脱离会话时 ⛔ 写 `setsid nohup …`,用 `nohup … &` 加 `disown`**(2026-08-19 dispatch 第三十三任实撞报修,中继 relay 第二任实测 `command -v setsid` 零输出后落卡)。`setsid` 是 Linux util-linux 的命令,macOS 不带 ⇒ **失败形态是「整条命令 exit 1、根本没跑」,不是「进程起来了又死了」**,而排查时人会一路往 Chrome/端口/profile 上找。⭐ **这是预防型落卡**:全库与全部技能卡此前对 `setsid` **零命中**(即没有人被它坑过的记录),立它的理由不是纠错,是它属于**「本机没有、但读起来完全合理」**那一类——任何人想让进程活过当前会话都会自然想到它,而它的失败方式有误导性。**成本一行,收益是省掉一次找错方向的排查。**

📌 **相关但不同的一件事(⛔ 混为一谈)**:lane 侧「后台进程活不过命令会话」是**环境级进程回收**,与 `setsid` 存不存在无关——已裁定走 `fresh` 时预起常驻 headless(11B #42;该修法落地时**宪法头第 12 条那段必须同轮改** —— ✅ 2026-08-20 已把宪法头模板第 12 条与本走查段双双改成两态:端口已监听⇒直接用⛔pkill,无监听才自起自清;⚠️ 仍未做的是 `cdp_sweep` 白名单——vdown/halt 回收窗口时仍按端口扫,会扫掉预起的常驻实例=#42 收方侧缺口,归 fresh --with-headless 落地一并做)。上面这条治的是**你写的命令没跑起来**,#42 治的是**跑起来了但活不过命令边界**。
