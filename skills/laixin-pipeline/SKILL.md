# laixin开发流水线(编排卡)

> 权威流程在 [[来信平台-开发协作流程]]"laixin开发流水线"节,本卡只给操作程序。
> 铁律一:**自动化只搬消息,不动闸门**——发车位纪律、验收七步(laixin-acceptance)、基点纪律原样执行。
> 铁律二:**状态永远在知识库,不在窗口记忆里**——执行总表(片级)+看板(事件流)随做随写,任何窗口随时可被换掉。
> 铁律三(2026-08-13 事故后立):**验收结论里的每个数字、每处代码引用,必须能在紧邻的真实工具返回中逐字找到**;记不起对应返回的,重新执行工具,不得凭印象书写。

## 0. 先确认你是哪个窗口

2026-08-13 起,原"执行窗口"按职能拆为两个:

| 你是 | 你做 | 你**不**做 |
|---|---|---|
| **派工窗口** | 写 prompt、`laixin-lane` 派工、监听交付与轨道状态、交接给验收窗口、收回执后合并、更新执行总表 | **不验收**(不许自己验自己派的片) |
| **验收窗口** | 只做独立验收:复现证据、跑全量、browser-harness 走查、rebase 后复跑、写验收记录、给结论 | **不写 prompt、不碰 lane、不合并** |

不确定时问创始人或方案窗口,**不要两个都干**——那就是拆窗口前的旧形态。

# A. 派工窗口

## 工具速查(`laixin-lane`,已在 PATH)

```bash
laixin-lane fresh a                        # 重启 A 轨=全新上下文(默认 ~/来信平台 主树)
laixin-lane fresh b --dir ~/来信平台-bN    # B 轨每片换 worktree(必须独立 worktree,不可用主树)
laixin-lane send a "好的,接下来开发 /Users/pingxia/Obsidian/项目入口/来信平台/知识库/4-开发层/prompt/<片名>开发prompt.md"
laixin-lane peek a 30                      # 抽查在飞状态;一律 ≥20 行,5 行只截到提示符会误判
LAIXIN_WINDOW=派工窗口 laixin-lane log "合并 客服-1 <commit> 195绿"   # ← 派工窗口记看板用 log
                                           #   vlog 是验收窗口专用(来源固定标"验收窗口"),你用了会记错来源
laixin-lane status / attach / down <a|b>

laixin-lane events status                  # 事件总线(dispatch 自动带起;交付+卡住事件投递)
laixin-lane handoff                        # 交班:客观半部机器生成,判断人写
laixin-lane claim                          # 接管派工角色的第一件事:认领派工权(send 会自动续期)
# 模型已显式钉死(2026-08-13 创始人裁定):验收/派工窗口 = claude-opus-5(agentic 主力档,验收要的是可靠核查
# 不是极限推理);方案窗口 = 创始人自选(Fable 5);lane Codex = gpt-5.6-terra。**不继承任何人的 /model 副作用**
# ——有人在方案窗口切模型存为默认,流水线成本不该因此翻倍。改档:LAIXIN_VERIFY_MODEL / LAIXIN_DISPATCH_MODEL。
laixin-lane whoholds                       # 谁当前持有派工权

laixin-lane watchdog start|stop|status     # 看门狗(需先 laixin-lane dispatch 托管派工窗口)
```

## 循环

**1. 派工(每轨一次只飞一片;每片全新上下文)**
- 核执行总表"进行中"节:该轨有片在飞 → 不发(发车位纪律);
- **先 `fresh` 再 `send`**——Codex 上下文不跨片,prompt 自包含(权威库直读);
- **`send` 之后必 `peek` 复核**:见 `Working`/`Explored`/`Read` 才算派工成功;只见提示符=消息被吞,重发;
- **发车前校准占号(机器执法)**:A 轨跑 `laixin-lane next-migration`,B 轨跑 `laixin-lane next-worktree`——未合并分支与未提交文件都占号,main 上 `ls` 看不见(0026/0033 两次实撞);prompt 里写死的号以此为准覆核;
- 发车后:总表"进行中"登记 + 看板记 `派工 <片名> → lane-<轨>`。

**2. 事件由事件总线投递(2026-08-13 第三轮:你不需要也不要自建 Monitor)**

`laixin-lane dispatch` 起窗时自动带起 `events` 窗口(纯 bash 常驻循环,看门狗会保它活着)。**监听不再随派工窗口死**——这正是 7.8h 停摆的直接机制(监听活在窗口进程里,窗口一换监听就停)。它投递三类:

- **【事件】交付落盘**:直接进你的输入框,含报告路径与末行,下一步通常就是 `verify-from`;
- **【告警】lane ≥6 分钟无变化**(空闲或卡住):自带该轨下一片提示与三选一强制动作(派工/现在写/总表写明),**不得静默**;
- **【告警】verify-* 窗口 ≥6 分钟无变化**:可能撞上需拍板的问题、卡在权限提示、或已回执未回收——**验收窗口没有自己的看门人,你就是**。

**你不在时**:交付事件(事实)**暂存 spool**,你一起来就补投;瞬时告警丢弃(没有行动者的告警没有意义)。查看:`laixin-lane events status`;日志 `~/.laixin-events.d/events.log`。

⚠️ 历史上的监听坑(按文件名收不到/内容标记被文档自触发/未带 mtime 漏掉整改重交/监听随窗口死)——**已全部被事件总线机器化吸收**,单一实现在 `laixin-lane ev-loop`,**别再手写监听**(手开临时接管、事件总线又起不来时才允许,方法见协作流程文档)。

⚠️ **仍归你人工判断的一条:交付信号≠事情做完**——若交付 commit 的提交时间早于你中途转发给该轨的裁定/整改要求,**拦下不交接**,等 amend 后的新信号(2026-08-13 实拦:转单-1 的 `e7c987e` 早于转单-7/8 裁定送达,amend 成 `b0b6e6d` 后才交验)。机器只报"落盘了",**"该不该进验收"是你的判断**。

**3. 交接给验收窗口(交付到达时)——一片一个,验完即弃**

优先用一步式(解析报告末行取分支与 commit,**防手抄 hash 笔误**,顺带机器校验交付契约与 commit 存在性):

```bash
laixin-lane verify-from "<交付报告绝对路径>" --prompt <prompt绝对路径> --to dispatch
```

或手动全参(报告末行不合契约、需要覆写时):

```bash
laixin-lane verify <片名> \
  --branch <分支> --commit <HEAD commit> \
  --report <交付报告绝对路径> --prompt <prompt绝对路径> \
  --to <你自己的会话名>          # 回执发给谁;不传则它自己 ListAgents 找
```

脚本会:在 tmux `laixin` 会话新开 `verify-<片名>` 窗口 → 起一个**全新 claude**(`--permission-mode auto` + 工具白名单/黑名单)→ 自动过信任与 MCP 提示 → 把五项客观信息派进去。约 15 秒返回。

- 复核:`laixin-lane peek-v <片名> 30`;观看:`laixin-lane attach`;列在跑的:`laixin-lane vlist`;
- 收到回执并合并后:`laixin-lane vdown <片名>` 回收(与 worktree 回收同理,不留残窗);
- 整改重验:先 `vdown` 再 `verify`(同名窗口不重复起);
- **交接后立刻释放主树**:`git -C /Users/pingxia/来信平台 checkout main`——验收窗口走独立验收树,不依赖主树分支;该片 commit 已落地、分支保留,切走不丢;打回时再 checkout 回原分支整改。**不切,"验收中不占发车位"在现场不成立**——台账说不占位、主树看着占位,**Codex 信现场,且它是对的**(2026-08-13 建库路径修复因此连拒两次)。若报 `fatal: 'main' is already used by worktree ...`:**空闲 worktree 占住了分支,先回收它**——回收 worktree 的真实理由是解发车阻塞,不是省磁盘。

⚠️ **绝不允许两个派工窗口同时活着**——两个窗口同时动 lane 会把 Codex 上下文搞乱(2026-08-13 实际险些发生,当时靠人工提醒才没撞)。**机器执法方式:派工权锁**。

- 接管派工角色**第一件事** `laixin-lane claim`;此后每次 `send` **自动续期**;
- `dispatch` 起窗时脚本代它认领;别的窗口来 `claim` 会被拒(除非持有者停止动 lane 超 30 分钟,或显式 `--force`);
- 看门狗在"dispatch 已死但派工权被别人新鲜持有"时**不自动重起**,只告警——那说明有人接管了。

> **为什么不用"数 tmux 外的活跃会话"来判**(曾如此实现,已换掉):数量是身份的**不可靠代理**——你开一个窗口只是问问题、和开一个窗口接管派工,在"数量"里长得一模一样。**基线设低会误判罢工,设高会在真撞车时不拦。** 而 `send` 是派工窗口的**定义性行为**:谁在动 lane 谁就是派工窗口 ⇒ **直接测行为,不猜身份。**

⚠️ **跨窗口移交的每条结论,都要附上得出它的那条命令**。2026-08-13 一天内双向各发生一次"把自己的推断当事实移交":①交接窗口把"商会申请审核状态"整个判为缺口,接班窗口核出接口早已返回;②接班窗口把 `categories.clarification_questions` 判为"字段挂错对象",而 `Category` 类恰好定义在 `demand.py` 文件里(按文件名推断会误读),复核后原文正确。**两次都是读代码得出的结论与代码本身之间那层推断,在传递中丢掉了不确定性标记。** 附上命令,接班方就能一秒复核;不附,它要么盲信、要么重查一遍。**接班窗口重验前任判断是应当鼓励的行为,不是不信任。**

⚠️ **交接只传那五项,不得附带你的判断、预期或"应该没问题"**——你写了 prompt,你的预期就是污染源。脚本发的指令模板已经是干净的,**不要手动追加评论**。

**为什么一片一个窗口**:验收是上下文消耗最大、也最容易凭印象书写的环节(2026-08-13 夜间编造事件全部发生在单片验收内部)。一次性窗口把"靠换班纪律压住"变成"结构上无法积累",与 Codex 每片 `fresh` 是同一条纪律。

**4. 交接的同一轮内,立即派该轨下一片**——**合并不是终点,派工才是**。验收期间该轨空闲是事故,不是等待。

**5. 收回执后收尾(每步记看板)**
- **通过**:回执含 `verify-*` 分支、其 commit、**所基于的 main commit**、全量结果。合并前**两道校验**:①`laixin-lane evidence <片名>` 复查——**回执里出现的每个数字都要能在证据文件里 grep 到,对不上即退回重验**(2026-08-13 编造事件的机器化防线);②**校验 `main` 仍等于回执里的 main commit**;已变动 → **退回验收窗口重跑**,不得直接合。合并 → 三处台账(log/执行总表/模块台账)→ 看板记 `合并 <commit> <用例数>` → 回收该片 worktree;
- **打回**:把验收窗口给的问题清单原样 `send` 回该轨(Codex 在原分支整改)→ 看板记 `打回 <片名> <一句话原因>`;**座位裁决(2026-08-13)**:打回整改进该轨**队首**(优先于一切排队片),但**不中断已开工的在飞片**——在飞片交付进验收后,座位先给整改(例外:整改片是在排片的阻塞性依赖且创始人在线,可请示中断;**夜间一律不中断**);
- **挂起**:**打回分两类,挂起判据不同(2026-08-13,分类权在验收窗口回执,派工窗口照执行、不自行改判)**——**方向性打回**(方向性问题/裁定缺口/红线争议/验收方判"需升级")**一次即挂起**;**工程打回**(实现缺陷、整改新引入的回归,验收方判"不需升级")可继续整改,**同一片累计三次才挂起**(防无限循环)。挂起 → 看板记 `挂起(<类型>)` → SendMessage 报方案窗口;**该轨停,另一轨照跑**;字面与实质冲突一律上报,不自行解释规则。

# B. 验收窗口

**你由 `laixin-lane verify` 起,一片一个窗口,验完即弃。** 收到派单后:

1. **先重读该片 prompt 与执行总表在飞节,再读交付报告**——不依赖窗口记忆(可能已被压缩);看板记 `验收开始 <片名>`;
2. 按 `laixin-acceptance` 七步独立验收:**全量自己跑、browser-harness 自己走查、报告没提的验证项就是最该亲手跑的**;判据是"全部 passed 且 zero failed",**不是测试数相等**(subTest 计数不稳);
3. **验收隔离**:主树可能被 A 轨 Codex 占用,一律走独立验收 worktree 或 ref 级操作(`commit-tree`/`branch -f`),**禁止在共享工作树 checkout/merge**;
4. 小口子自行修复并在验收记录写明;方向性问题打回;
5. **最后一步必须是:rebase 到当时 main,并在 rebase 后的状态上复跑全量**——"验的就是合的";
6. `SendMessage` 回派工窗口:
   - 通过 → `verify-*` 分支名 · 其 commit · **所基于的 main commit** · 全量结果;
   - 打回 → 逐条可复现的问题清单 + **打回类型(方向性/工程,分类权在你)** + 是否需升级创始人;
7. 在同一份记录文件追加"验收方独立验收结论"节;看板记 `验收通过` 或 `打回`。

**你不自行 `laixin-lane send`**,即使判定打回也经派工窗口转发——两个窗口同时对一条 lane 发消息会造成 Codex 上下文错乱。

**回执发出后你的活就结束了**——不要找新活干,等派工窗口 `vdown` 回收你即可。(历史片的"零命中"结论复核是另派的独立任务,不是你顺手做的事。)

**工具层已给你上的锁**(不必自觉,也绕不过):`git push` / `git merge` / `git reset --hard` / 一切 `laixin-lane send|fresh|up|down` 均被 `--disallowedTools` 硬拒。记看板用 `laixin-lane vlog "..."`(**不要写 `LAIXIN_WINDOW=... laixin-lane log`**——带 env 前缀的命令不匹配白名单,会平白卡一次权限提示)。

## 上下文换班纪律(按证据量分档)

- **Codex**:每片 `fresh`,不存在积累问题;打回整改不 fresh(分支现场就是它的记忆);
- **验收窗口:一片一个,不换班也不复用**(`laixin-lane verify` 起、`vdown` 收)——一次全量输出+一份 diff 复核就能吃掉可观上下文,2026-08-13 夜间的编造事件正是连续验收多片后发生的;一次性窗口让上下文结构上无法积累;
- **派工窗口:四轨判断,任一触发即交班**(2026-08-13 定,取代原"4-6 片"单一判据):

| 轨 | 判据 | 性质 |
|---|---|---|
| ① 上下文 | `laixin-lane ctx` **≥70%** | **硬闸门**,留 30% 给交接与收尾 |
| ② 片数 | 派工 **8-10 片** | 常规节奏 |
| ③ 行为信号 | ⓐ 开始用"重新查证"代替凭记忆;ⓑ **记不清某数字来自哪次工具返回** | ⓑ **出现即交,不留余地**——编造的直接前兆 |
| ④ 错误信号 | ⓐ 台账出现遗漏或前后不一致;ⓑ 被下游(Codex/验收窗口/接班窗口)纠正过判断 | 判断力下滑的证据 |

  ⚠️ **不能用 `/usage` 的 "cache write" 反推上下文**(2026-08-13 两次实测,方向相反):
  | 读法 | 得数 | 实际 | 偏差方向 |
  |---|---|---|---|
  | 从 `/usage` cache write 反推(样本一) | "约 50%" | 54.9% | 偏低 |
  | 把 `/usage` cache write 当成当前上下文(样本二) | "快 700K" | 44.5% | 偏高 |

  **`cache write` 是整个会话的累计写入量**(一次会话 377 次请求,每次写一点,累计 998k——已超过 1M 窗口本身,足以反证它不是"当前装着多少")。当前上下文只有一个来源:**transcript 最后一条 `usage` 的 `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`**——三者互斥,相加即本次请求总输入。`laixin-lane ctx` 存在的理由就是这个。
  ⚠️ **多窗口环境下 `ctx` 不带参数会取错**:它按 mtime 排,而本机同时跑着方案/派工/验收多个会话。**查自己一律 `laixin-lane ctx <你的 session 前 8 位>`**(在 scratchpad 路径里)。不带参数时它会列出所有会话让你认领,不猜。

  ⚠️ **绝不能凭感觉判断该不该交班**。实测(拿一个真实派工窗口做样本):自评"30-40%",`/usage` 反推"约 50%",**transcript 精确读数 54.9%** ⇒ **自我感知低估 15-25 个百分点**。感觉只能触发检查,**判据必须是 `ctx` 读数**。
  ⚠️ **①②必须并存,它们管不同的风险**:顺利时纯派工约 34k/片,8 片才吃 27%,这时片数闸门先到;但事故(误判调查、网页查证、复核)能让 4 片就烧到 55%。**片数管常规节奏,占比管意外——而事故恰恰在长会话里更容易发生,只靠片数计数器,它会在最该报警时走得最慢。**
  **交班动作**:每合并一片后 `laixin-lane ctx` 自检 → 命中即**先把状态写完整**(总表进行中 + 看板轨道快照 + log)→ 写交接包 → `laixin-lane dispatch --fresh` 起新窗口 → **确认新窗口已接管后才收工**;
- 任一窗口自觉开始翻旧消息找状态,就是该换班了。换班时:看板记 `换班`+更新"轨道快照"节。**若派工窗口已被看门狗托管,换班不需要人**——`laixin-lane dispatch --fresh` 即可换全新上下文,看门狗也会在它死后自动这么做;
- **新窗口起手式**:`laixin-lane doctor`(体检,会查事件总线在不在)→ 调 Skill laixin-pipeline → 认领角色 → `laixin-lane stats`(燃料+片级周期)→ 读执行总表"进行中"+看板末 20 行 → 接管。**不需要重建 Monitor**——事件总线独立于窗口存活,你不在时的交付已在 spool 里等你;
- **交班时先 `laixin-lane handoff`**:客观半部(main/拓扑/验收窗口/派工权/事件总线/燃料/周期/看板尾)机器生成,**你只写判断——且逐条标明是判断、附得出它的命令**;
- **方案窗口**:设计落库即窗口可弃,接续走记忆+index.md。

## 夜间无人值守(创始人睡觉,流水线照跑)

> **2026-08-13 实测教训**:流水线建成后的头 11.4 小时里,**8.4 小时(73%)是静默的,最长一段 7.8 小时正好是创始人睡觉时间**。根因不是纪律松,是**整条流水线的存活依赖"有一个活着的窗口"**:上一个窗口写完换班快照就收工了,而"开新窗口"只有人能做。**轨道空闲告警再完善也没用——告警发给了一个已经不存在的窗口。**
> 解法是看门狗(`laixin-lane watchdog`):纯 bash 常驻循环,不累不崩没有上下文,是整条流水线里唯一不会忘事的东西。派工窗口死了它重起,叫不醒它先戳后换。**但它只解决"没人派",解决不了"没片可派"**——夜间能跑多久取决于队列燃料,用 `laixin-lane stats` 看。

- 只做**排队节已 ready** 的片;prompt 没写好的不现场发挥;
- 工程打回可继续整改(同一片累计三次才挂);**方向性打回或任何裁定缺口一次即挂起该轨**,绝不代拍裁定、不吵醒创始人;**夜间一律不中断在飞片**;
- 合并照常(验收全过才合,标准不因夜间降低);
- 早晨交班:看板事件流就是夜报,方案窗口向创始人汇总"合了什么/挂了什么/为什么"。

## 窗口间通信

- `ListAgents` 找对方,`SendMessage` 互发;方案窗口发**设计与裁定**,派工窗口回**片级事实**(合入 commit/用例数/挂起原因),验收窗口只与派工窗口对接;
- **任何监听事件或消息到达,必须在同一轮内完成「判断 → 行动 → 可见输出」**;只调工具不产出可见结论,在外部看来与卡死无异;
- 创始人人工消息(attach 或任一窗口直接发话)与流水线消息等效,人工优先。

## 已知边界

- **起窗被专线自检拦截**(2026-08-13 实撞:readiness FAIL → claude 拒启 → 验收窗口没起来):`verify`/`dispatch` 现在会**秒级报出 FAIL 项并记看板**,不再哑等 90s。处置:①这是 fail-closed 保护(封号风险>停摆),**绝不绕过**;②修专线问题(`us-status` / `bash dns-guard.sh`),修好重试;③方向不明升级创始人。夜间流水线因此停摆是**正确行为**,早晨看板会有 ⛔ 记录;
- lane 里 Codex 崩了:`peek` 见 shell 提示符 → `fresh` 重启 → 重发当前片路径(Codex 从分支现场续);
- 迁移片验收必跑回环;B 轨零迁移核 `git diff main --stat`;
- prompt 写死的 worktree 号会失效,**发车前校准**;片合并/验收结束后即回收 worktree(`git worktree remove`)——**真实理由是解发车阻塞,不是省磁盘**:git 不允许两棵树 checkout 同一分支,空闲验收树占着 `main` 会卡住主树 `checkout main`(2026-08-13 实撞);
- 本卡不复制红线/术语/机制——照 kickoff/acceptance 卡指路去索引表。
